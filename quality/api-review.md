# Claude API による問題の点検(2026-11-12 に用意)

問題(日本語と、英語・繁体字・韓国語の訳)の事実確認を、Claude API の Message Batches でまとめて頼む仕組みです。プロジェクトの手順にある「書いた本人とは別の点検者」の役を担います。

- 出力は**指摘の候補**です。反映は、これまでどおり1件ずつ確かめてから行い、見送った指摘は理由とともに [audit.md](audit.md) に残します
- 道具は問題データを読むだけで、書き換えません
- 外部のライブラリは使わず、Node 標準の `fetch` で API を呼びます(`tools/api-review.js`)

## 運営者がすること(1回だけ)

1. Claude Console で API キーを作る
2. GitHub のリポジトリの Settings → Secrets and variables → Actions → New repository secret で、名前 `ANTHROPIC_API_KEY` として登録する(キーは会話やコードに貼らない)

## 動かし方(GitHub の Actions → API review → Run workflow)

| action | すること | キー |
|---|---|---|
| estimate | 見積もりだけ。送信しない | 不要 |
| submit | 見積もりが上限以内なら送信し、結果が出るまで待って保存する(多くは1時間以内、最長24時間) | 必要 |
| fetch | 送信済みで、待ちきれなかったバッチの結果を取りにいく | 必要 |
| status | 処理の状況を見る | 必要 |

- `cats`: 分野の ID(カンマ区切り)か `all`。excludeCats の分野は指定できない
- `max_usd`: 今回の上限額。**最悪の場合の額**(キャッシュが一度も当たらず、全件が出力の上限まで出た場合)がこれを超えると送信しない
- `total_cap_usd`: 累計の上限額。これまでの実費(結果待ちのものは最悪の額)と合わせて判定する
- 結果は `api-review-results` ブランチの `quality/api-review/runs/<日時>/` に入る。`report.md` が人の読む一覧、`findings.json` が機械で扱う一覧、`ledger.json` が費用の記録。main とサイトの公開には影響しない

手元で見積もるとき: `node tools/api-review.js estimate --cats mosfet,bjt`(キーがあれば `--count` で公式の count_tokens による実測に切り替わる)

## 費用の見積もり(2026-11-12、文字数からの概算)

全60分野・2,957問・4言語、Claude Opus 5.5、effort high、8問ずつ406件のとき:

- 目安 約 $34(1件の出力を6,000トークンと仮定)
- 最悪 約 $124(上限の判定に使う額)

実費は結果の `usage` から計算して `ledger.json` に残す。最初は2〜3分野で試し、1件あたりの実費と指摘の質を見てから全体を流す。

## 作りの要点と根拠

- **Batch API**: 標準の半額。1バッチは10万件か256 MBまで。結果は29日間取れる。`stream`・`speed`・`fallbacks`・`max_tokens: 0` は使えない(2026-11-12 に公式の Batch processing の文書で確認)
- **プロンプトキャッシュ**: 共通の点検の指示(standards.md と CONTENT_QUALITY_GUIDELINES.md を含む)と、分野ごとの用語集を、1時間のキャッシュにする。バッチは5分を超えて処理されることがあるため、公式の文書は1時間を勧めている。キャッシュの書き込みは入力単価の2倍、読み出しは大幅に安い。バッチ内のキャッシュは当たるとは限らないので、上限の判定は「当たらない」前提で行う
- **料金**(Batch、USD / 100万トークン): Opus 5.5 入力 2・出力 10、Sonnet 5.5 入力 1・出力 5、Haiku 5.5 入力 0.05・出力 0.25(公式の Batch processing の表)。考える分のトークンも出力として課金され、`max_tokens` に含まれる
- **出力の形**: 構造化出力(`output_config.format` の JSON スキーマ)で、ID・言語・欄・種類・優先度・確度・要出典・抜き出し・問題・直し方の案を返させる
- **点検の観点**: 正解を見ずに解いて照合、解説と補足と正解の整合、計算の検算、過去に繰り返した誤りの4つの型、解説に書かない情報(年・版・市場の数値など)、訳の意味の一致と用語集の用語名(繁体字は台湾の用語)。GPU・AI・性能チューニングの記述は記憶で正しいと判断させず、要出典として出させる
- **ウェブ検索は使っていない**。点検者も記憶で判断しているので、要出典の指摘や確度の低い指摘は、公式の文書・原論文で確かめてから反映する

## 結果の扱い

1. `report.md` を分野ごとに読み、P0 と確度 high から確かめる
2. 正しいと確かめた指摘だけ、問題データと訳を直す(訳を直したら `node tools/i18n-stale.js --update <言語>`)。いつもの4つの検査を通して公開する
3. 確かめた方法(検算した、公式の文書で照合した、など)と、見送った指摘とその理由を audit.md に書く
4. 「結果が得られなかった依頼」(拒否・出力切れ・読めない出力)は、`--ids` で問題を絞って出し直す
