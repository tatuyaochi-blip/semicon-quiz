정적 링킹 vs 동적 링킹: 차이점 설명

링킹은 컴파일된 코드를 그 코드가 사용하는 라이브러리 코드와 결합하는 과정입니다. 정적 링킹에서는 필요한 라이브러리 코드가 빌드 시점에 실행 파일에 복사되므로 프로그램이 독립적으로 동작합니다. 동적 링킹에서는 실행 파일이 필요한 공유 라이브러리만 기록해 두고, 운영체제가 프로그램 시작 시 이를 로드하므로 여러 프로그램이 하나의 사본을 공유할 수 있습니다. 정적 링킹은 배포가 더 간단하고, 동적 링킹은 메모리를 절약하며 업데이트가 쉽습니다.

비교 항목정적 링킹동적 링킹
수행 시점빌드 시점: 라이브러리 코드가 실행 파일에 복사됨로드 시점 또는 실행 시점: 동적 링커가 공유 라이브러리(.so, .dll)를 찾아 매핑함
실행 파일 크기큼작음
메모리 사용각 프로그램이 라이브러리 코드 사본을 따로 가짐공유 라이브러리 하나를 여러 프로세스가 공유할 수 있음
업데이트와 보안 패치프로그램을 다시 빌드하고 재배포해야 함라이브러리를 한 번만 업데이트하면 재빌드 없이 모든 프로그램이 혜택을 봄(인터페이스가 호환되는 경우)
시작 시간약간 빠름약간 느림: 심볼을 해석해야 함(대개 지연 방식)
배포독립적: 라이브러리가 설치되어 있지 않아도 실행됨대상 시스템에 올바른 버전의 라이브러리가 필요하며, 없으면 프로그램이 시작되지 않음
실행 시간 비용프로그램 전체 최적화와 직접 호출 가능GOT와 PLT를 거치는 간접 호출로 인한 작은 오버헤드
버전 문제실행 시점에는 없음프로그램과 설치된 라이브러리 간 불일치 가능
주요 용도임베디드 펌웨어, 단일 파일 도구, 최소 컨테이너범용 운영체제의 대부분의 프로그램, 플러그인, libc 같은 시스템 라이브러리

수치는 대략적인 자릿수 기준이며, 공정 세대와 제품에 따라 달라져요.

상황별 선택 기준

정적
어디서나 실행되는 독립적인 바이너리가 필요하거나, 임베디드 펌웨어처럼 운영체제 로더가 없을 때.
동적
여러 프로그램이 같은 라이브러리를 공유하며 메모리를 절약하고 라이브러리를 중앙에서 패치하고 싶을 때.

자주 묻는 질문

프로그램이 라이브러리 누락 오류로 실행되지 않는 이유는 무엇인가요?

동적으로 링크된 프로그램인데, 필요한 공유 라이브러리(.so 또는 .dll 파일)가 해당 컴퓨터에 설치되어 있지 않기 때문입니다. 라이브러리를 설치하거나 프로그램을 정적으로 링크하세요.

동적 링킹은 메모리를 절약하나요?

그렇습니다. RAM에 있는 공유 라이브러리 하나를 여러 프로세스가 공유할 수 있습니다.

정적 링킹이 더 빠른가요?

약간 빠릅니다. 시작 시 심볼 해석과 GOT, PLT를 통한 간접 호출을 피할 수 있고, 프로그램 전체 최적화도 가능합니다.

동적 링킹이 보안 업데이트에 유리한 이유는 무엇인가요?

공유 라이브러리를 한 번만 패치하면 그것을 사용하는 모든 프로그램이 재빌드 없이 혜택을 받기 때문입니다.

이해도 확인

정적 링크에 대한 설명으로 올바른 것은?

  1. A사용하는 라이브러리의 코드를 실행 파일 안에 복사하여 결합한다
  2. B프로그램을 실행할 때마다 라이브러리를 읽어 들여 결합한다
  3. C라이브러리를 쓰지 않고 모든 처리를 하나의 소스 파일에 쓴다
정답과 해설 보기

정답: A. 사용하는 라이브러리의 코드를 실행 파일 안에 복사하여 결합한다

정적 링크에서는 링커가 정적 라이브러리(Linux에서는 .a 파일)에서 필요한 함수를 꺼내 실행 파일에 포함시킵니다. 실행 환경에 라이브러리가 없어도 동작하고 시작할 때 결합하는 수고도 없지만, 실행 파일이 커지고 같은 라이브러리를 쓰는 프로그램마다 사본을 가지게 됩니다. 라이브러리의 결함이 수정되어도 다시 빌드하지 않으면 반영되지 않습니다.

동적 링크(공유 라이브러리)의 이점으로 올바른 것은?

  1. A실행 환경에 라이브러리가 없어도 반드시 동작한다
  2. B여러 프로그램이 하나의 라이브러리를 메모리 상에서 공유할 수 있고, 라이브러리를 갱신하면 다시 빌드하지 않아도 수정이 반영된다
  3. C시작 시 처리가 전혀 필요 없어져 정적 링크보다 반드시 빠르게 시작한다
정답과 해설 보기

정답: B. 여러 프로그램이 하나의 라이브러리를 메모리 상에서 공유할 수 있고, 라이브러리를 갱신하면 다시 빌드하지 않아도 수정이 반영된다

동적 링크에서는 실행 파일에 「어느 공유 라이브러리의 어느 함수를 사용하는가」만 기록하고, 실행할 때 동적 링커가 라이브러리를 읽어 들여 연결합니다. 공유 라이브러리의 코드는 바뀌지 않으므로 물리 메모리 상의 하나의 사본을 많은 프로세스가 공유할 수 있습니다. 결함이나 취약점의 수정도 라이브러리를 교체하기만 하면 끝납니다. 다만 시작할 때 결합하는 수고가 듭니다.

동적 링크를 사용한 프로그램을 다른 컴퓨터에 복사해 실행했더니 시작되지 않았다. 가장 가능성이 높은 원인은?

  1. A실행 파일 안에 라이브러리 코드가 모두 들어 있어 너무 컸기 때문
  2. B동적 링크 프로그램은 만든 컴퓨터에서만 동작한다는 규칙이 있기 때문
  3. C필요한 공유 라이브러리가 설치되어 있지 않거나, 호환되지 않는 버전만 있기 때문
정답과 해설 보기

정답: C. 필요한 공유 라이브러리가 설치되어 있지 않거나, 호환되지 않는 버전만 있기 때문

동적 링크 프로그램은 실행하는 컴퓨터에 있는 공유 라이브러리를 사용합니다. 필요한 라이브러리가 없거나 함수가 부족한 오래된 버전만 있으면 동적 링커가 결합하지 못해 시작에 실패합니다. Linux에서는 ldd 명령으로 프로그램이 필요로 하는 공유 라이브러리와 그것이 발견되는지를 확인할 수 있습니다. 배포하기 쉽도록 일부러 정적 링크로 만들기도 합니다.

  1. 정적 라이브러리(.a 파일)와 함께 링크할 때 링커가 실행 파일에 포함시키는 것으로 올바른 것은?
  2. 공유 라이브러리에서 사용되는 GOT(전역 오프셋 테이블)의 역할로 올바른 것은?
  3. 100개의 프로세스가 같은 공유 라이브러리를 사용하고 있을 때, 물리 메모리 사용 방식으로 올바른 것은?

링커, 로더, 실행 파일 문제 풀기

주요 용어 설명

정적 링크(static linking)
사용하는 라이브러리의 코드를 실행 파일에 복사해 넣는 링크 방식입니다. 라이브러리가 없어도 실행되지만 파일이 커지고, 라이브러리를 수정하면 다시 빌드해야 합니다.
동적 링크(dynamic linking)
실행 시에 공유 라이브러리를 적재하고 연결하는 링크 방식입니다. 프로세스 간에 라이브러리를 공유하고 교체만으로 수정할 수 있지만, 호환되는 라이브러리가 시스템에 있어야 합니다.
공유 라이브러리(shared library)
동적 링크로 실행 시에 적재되는 라이브러리로, Linux에서는 .so, Windows에서는 .dll입니다. 위치 독립 코드로 만들어져 코드 페이지를 여러 프로세스가 공유할 수 있습니다.
정적 라이브러리(static library)
여러 오브젝트 파일을 묶은 아카이브입니다(Linux에서는 .a). 정적 링크 시 링커가 필요한 오브젝트만 꺼내 실행 파일에 넣습니다.
