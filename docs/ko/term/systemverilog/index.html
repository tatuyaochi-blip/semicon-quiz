SystemVerilog란?

Verilog를 확장한 언어. logic형과 always_ff·always_comb 등의 설계 기능, 클래스, 제약 조건 랜덤, 어서션 등의 검증 기능을 갖는다.

일본어 명칭: SystemVerilog

SystemVerilog은(는) HDL과 검증, IC 설계 흐름과 EDA 등 2개 분야의 연습 문제 10개에 나와요.

분야: HDL과 검증

SystemVerilog가 설계에 추가한 것

IEEE 1800으로 표준화된 SystemVerilog는 Verilog의 상위 집합으로, 하드웨어를 기술하는 기능과 이를 검증하는 기능을 모두 추가합니다. 설계 측면에서는 logic 타입이 단일 드라이버 신호에 대해 Verilog의 헷갈리는 wire/reg 구분을 대체하고, always_ff, always_comb, always_latch가 의도한 하드웨어를 명시하며, enum, struct, package, interface가 RTL을 더 읽기 쉽고 오류가 적게 만듭니다. Verilog에서 reg는 always 블록에서 할당되는 신호를 뜻할 뿐 반드시 플립플롭은 아닙니다. 트라이스테이트 버스처럼 드라이버가 여러 개인 신호에는 여전히 wire를 사용하며, logic은 X와 Z를 가질 수 있는 4값 타입입니다.

RTL 실수를 조기에 잡기

Verilog에서 흔한 버그는 의도하지 않은 래치입니다. 조합 always 블록이 어떤 경로에서 출력을 할당하지 않으면 도구는 이전 값을 기억할 수밖에 없습니다. 표준적인 해결책은 블록 맨 앞에서 모든 출력에 기본값을 할당하는 것입니다. always_comb를 사용하면 도구도 조합 논리가 의도되었음을 알고 래치가 추론될 때 경고나 오류를 내며, 감도 목록이 읽는 신호로부터 자동으로 만들어지므로 손으로 쓴 목록에서 신호를 빠뜨리는 실수도 피할 수 있습니다. always_ff도 마찬가지로 에지 트리거 플립플롭에 대응되지 않는 코드를 지적합니다.

검증 기능

SystemVerilog의 추가 기능 대부분은 테스트벤치를 위한 것입니다. 클래스는 객체 지향 프로그래밍을 도입하고, 제약 조건 랜덤 생성은 워드 정렬된 주소나 1부터 256까지의 길이 같은 유효한 자극을 만들어 내며, 커버그룹은 기능 커버리지를 측정해 어떤 경우가 실행되었는지 보여 줍니다. SystemVerilog Assertions(SVA)는 요청 후 3사이클 이내 응답 같은 시간적 속성을 표현하며, 이는 시뮬레이션에서 검사되거나 포멀 도구로 증명됩니다. 클로킹 블록은 테스트벤치 신호를 구동하고 샘플링하는 시점을 정의해 설계와의 레이스를 막습니다. UVM(Universal Verification Methodology, IEEE 1800.2)은 이 기능들 위에 재사용 가능한 테스트벤치를 구축합니다.

합성 가능한 코드와 테스트벤치 전용 코드

SystemVerilog의 일부만 하드웨어를 기술합니다. logic, always_ff, always_comb, enum, struct, package, interface를 포함한 합성 가능한 부분 집합은 합성 도구가 받아들여 게이트로 변환합니다. 클래스, 랜덤화, 커버리지, 대부분의 동적 데이터형은 시뮬레이션에만 존재하며 설계를 둘러싼 환경을 기술합니다. 어서션은 RTL에 바인딩해 시뮬레이션, 포멀 검증, 때로는 에뮬레이션에서 사용할 수 있지만 기능 논리로 변환되지는 않습니다. VHDL은 특히 일부 FPGA 팀과 항공우주 분야 팀에서 여전히 주요 대안 언어입니다.

정답: C. UVM(Universal Verification Methodology)

UVM은 SystemVerilog로 테스트벤치를 부품(입력을 주는 드라이버, 출력을 감시하는 모니터, 기댓값과 비교하는 스코어보드 등)의 조합으로 구성하기 위한 표준 방법론이자 클래스 라이브러리입니다. 부품을 다른 설계의 검증에도 재사용할 수 있고, 제약 조건 기반 랜덤 입력 생성이나 커버리지 수집을 쉽게 포함할 수 있습니다. IEEE 1800.2로 표준화되어 있습니다. OPC와 CMP는 제조 기술입니다.

SystemVerilog의 제약 조건 랜덤 검증(constrained-random verification)에 대한 설명으로 올바른 것은?

  1. A입력 값을 사양에서 허용하는 범위나 조합 조건(제약) 안에서 랜덤하게 만들어, 사람이 생각하지 못한 경우까지 포함하여 폭넓게 시도한다
  2. B입력 값을 완전히 무작위로 만들어 사양에 없는 값도 많이 준다
  3. C입력 값을 사람이 모두 직접 작성한다
정답과 해설 보기

정답: A. 입력 값을 사양에서 허용하는 범위나 조합 조건(제약) 안에서 랜덤하게 만들어, 사람이 생각하지 못한 경우까지 포함하여 폭넓게 시도한다

사람이 생각한 테스트(지정형 테스트)만으로는 설계자가 상정하지 못한 조합의 불량을 놓치기 쉽습니다. 제약 조건 랜덤 검증에서는 예를 들어 '주소는 4의 배수', '길이는 1~256'과 같은 제약을 작성하고 그 안에서 랜덤하게 입력을 만들기 때문에, 의미 있는 입력만으로 많은 경우를 시도할 수 있습니다. 어떤 경우를 시도했는지는 커버리지로 측정하며, 부족한 부분은 제약을 바꾸거나 지정형 테스트로 보완합니다.

자주 묻는 질문

Verilog와 SystemVerilog의 차이는 무엇인가요?

SystemVerilog는 Verilog의 상위 집합으로, logic, always_ff, always_comb 같은 더 안전한 설계 구문과 클래스, 제약 조건 랜덤 자극, 기능 커버리지, 어서션 같은 검증 기능을 추가했습니다. 기존 Verilog 코드는 대체로 유효한 SystemVerilog입니다.

SystemVerilog는 합성 가능한가요?

logic, always_ff, always_comb, struct, enum, interface를 포함한 설계용 부분 집합은 합성 가능합니다. 클래스, 랜덤화, 커버그룹 같은 검증 구문은 시뮬레이션 전용입니다.

wire와 reg 대신 logic을 써야 하나요?

드라이버가 하나인 신호라면 logic은 assign 문으로 구동되든 always 블록으로 구동되든 동작하므로, 대부분의 코드에서 둘을 모두 대체합니다. 트라이스테이트 버스처럼 드라이버가 여러 개인 넷에는 wire를 사용합니다.
