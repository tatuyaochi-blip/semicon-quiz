핸드셰이크(Handshake)란?

송신 측의 요구(req)와 수신 측의 응답(ack)을 주고받아 데이터를 확실하게 전달하는 방식. 클록 도메인 사이에서는 req와 ack만 동기화하고 그동안 데이터를 고정해 두므로 안전하지만, 1회 전송에 수 사이클 이상 걸린다.

일본어 명칭: ハンドシェイク

핸드셰이크(Handshake)은(는) 타이밍 분석과 CDC, I/O 인터페이스와 버스, 논리 회로 등 3개 분야의 연습 문제 7개에 나와요.

분야: 타이밍 분석과 CDC

4상 시퀀스

4상(return-to-zero) 핸드셰이크에서는 먼저 송신 측이 버스에 데이터를 올려 유지한 다음 req를 올립니다. 수신 측은 동기화된 req를 보고 데이터를 캡처한 뒤 ack를 올립니다. 송신 측은 동기화된 ack를 보고 req를 내리고, 수신 측은 req가 내려간 것을 보고 ack를 내립니다. 각 신호가 한 번씩 오르내리므로 전송 한 번에 천이가 네 번입니다. 핵심 규칙은 순서입니다. 데이터는 req가 오르기 전에 안정되어 있어야 하고 ack가 캡처를 확인할 때까지 바뀌면 안 되며, 그렇지 않으면 수신 측이 변하는 도중의 값을 잡을 수 있습니다.

클록 도메인 사이에서 안전한 이유

도메인 사이를 건너는 것은 req와 ack뿐이며, 각각 일반적인 2단 플립플롭 동기화 회로를 거치는 단일 비트입니다. 멀티비트 데이터는 결코 동기화되지 않습니다. 수신 측이 req를 볼 때쯤이면 데이터는 이미 여러 사이클 동안 안정되어 있어 바로 캡처할 수 있습니다. 이로써 버스를 비트별로 동기화할 때 생기는 비트 스큐 문제가 사라지고, 어떤 주파수 비에서도 동작하며, 송신 측이 확인을 기다리므로 사건을 잃지 않습니다. 이 기다림이 사건 사이에 최소 간격을 보장해야 하는 토글 동기화와의 차이점입니다.

대가는 지연 시간

모든 천이는 동기화 회로를 거쳐야 하고 보통 한 방향에 2사이클이 걸리며, 4상 신호는 왕복이 두 번 필요하므로 전송 한 번에 두 도메인을 합쳐 8사이클 이상이 듭니다. 2상 방식은 req나 ack의 토글 하나하나를 사건으로 다루어, 엣지 검출 로직이 필요한 대신 천이 수를 절반으로 줄입니다. 어느 쪽이든 처리량은 사이클당 한 워드에 훨씬 못 미치므로, 핸드셰이크는 제어 레지스터 쓰기처럼 가끔 일어나는 전송에 적합하고 스트리밍 데이터는 비동기 FIFO를 거칩니다.

단일 클록 안의 핸드셰이크: VALID/READY

같은 요청–응답 개념은 동기화 회로 없이 동기식 버스에서도 쓰입니다. AXI에서는 모든 채널이 송신 측의 VALID와 수신 측의 READY를 사용하며, 둘 다 1인 클록 엣지에서 전송이 일어납니다. READY를 low로 유지하면 백프레셔가 걸리므로 속도가 다른 블록들을 데이터 손실 없이 연결할 수 있습니다. 데드록을 피하려면 송신 측은 READY를 기다린 뒤에 VALID를 올려서는 안 됩니다. AXI에는 읽기 주소, 읽기 데이터, 쓰기 주소, 쓰기 데이터, 쓰기 응답의 다섯 개 독립 채널이 있으며, AXI4-Stream은 단방향 데이터 흐름을 위해 주소를 없앴습니다.

도전해 보기: 핸드셰이크(Handshake) 관련 문제

req와 ack를 사용하는 4상 핸드셰이크로 데이터 하나를 전달할 때의 신호 순서로 올바른 것은?

  1. Areq를 1로 함과 동시에 데이터를 바꾸기 시작한다 → 수신 측이 ack를 1로 한다 → req와 ack를 동시에 0으로 한다
  2. B수신 측이 먼저 ack를 1로 한다 → 송신 측이 데이터를 확정하고 req를 1로 한다 → 수신 측이 데이터를 캡처한다 → req와 ack를 동시에 0으로 한다
  3. C데이터를 확정하고 req를 1로 한다 → 수신 측이 데이터를 캡처하고 ack를 1로 한다 → req를 0으로 한다 → ack를 0으로 한다
정답과 해설 보기

정답: C. 데이터를 확정하고 req를 1로 한다 → 수신 측이 데이터를 캡처하고 ack를 1로 한다 → req를 0으로 한다 → ack를 0으로 한다

4상 핸드셰이크에서는 req와 ack가 각각 한 번씩 올라갔다 내려가, 합계 4번의 변화로 한 번의 전달이 끝납니다. 송신 측은 데이터를 확정한 뒤 req를 올리고, 수신 측은 동기화한 req를 보고 데이터를 캡처한 뒤 ack를 올립니다. 송신 측은 동기화한 ack를 보고 req를 내리고, 수신 측은 req가 내려간 것을 보고 ack를 내립니다. req와 ack는 1비트이므로 2단 동기화기로 안전하게 전달할 수 있습니다. 데이터를 바꾸면서 req를 올리면 수신 측이 변화 중인 값을 캡처할 우려가 있습니다.

핸드셰이크를 이용한 클럭 도메인 간 데이터 전송의 단점으로 올바른 것은?

  1. Areq와 ack의 동기화를 왕복시키므로 1회 전송에 여러 사이클이 걸려, 연속적인 대량 전송에는 적합하지 않다
  2. B멀티비트 데이터를 전달하면 비트별 동기화 어긋남으로 데이터가 깨진다
  3. C송신 측과 수신 측의 클럭 주파수가 같지 않으면 사용할 수 없다
정답과 해설 보기

정답: A. req와 ack의 동기화를 왕복시키므로 1회 전송에 여러 사이클이 걸려, 연속적인 대량 전송에는 적합하지 않다

4상 핸드셰이크에서는 req가 수신 측에 전달되기까지 동기화의 2사이클, ack가 송신 측에 돌아오기까지 2사이클이 걸리고, 각각이 0으로 돌아가는 데도 같은 만큼 걸리므로, 1회 전송에 양쪽 도메인을 합쳐 8사이클 이상이 걸립니다. 그래서 제어 레지스터의 설정값처럼 가끔 전달하는 데이터에 적합합니다. 데이터는 전송하는 동안 계속 안정되어 있으므로 비트 어긋남으로 인한 오류는 일어나지 않으며, 주파수 비도 상관없습니다. 매 사이클처럼 데이터를 흘려보낼 때는 비동기 FIFO를 사용합니다.

자주 묻는 질문

2상 핸드셰이크와 4상 핸드셰이크의 차이는 무엇인가요?

4상 방식에서는 req와 ack가 각각 올라갔다가 0으로 돌아오므로 전송 한 번에 천이가 네 번 쓰입니다. 2상 방식에서는 모든 토글이 사건이므로 전송에 천이가 두 번만 필요해 지연 시간이 대략 절반이 되지만, 엣지 검출이 필요합니다.

AXI VALID/READY 핸드셰이크에 동기화 회로가 필요한가요?

아닙니다. VALID/READY는 단일 클록 도메인 안에서 동작하며 둘 다 high인 엣지에서 전송합니다. AXI 트래픽이 클록 도메인을 넘어야 할 때는 보통 비동기 FIFO로 구성한 비동기 브리지를 삽입합니다.

클록 도메인 크로싱에서 req/ack 핸드셰이크가 느린 이유는 무엇인가요?

req와 ack의 천이마다 여러 사이클의 동기화 회로를 거치고 송신 측이 응답을 기다려야 하므로, 전송 한 번에 8사이클 이상이 걸립니다. 가끔 보내는 데이터에는 괜찮지만 연속 스트림에는 맞지 않습니다.
