SQL 인젝션(SQL Injection)란?

웹 애플리케이션이 이용자의 입력을 그대로 이어 붙여 SQL 문을 조립한다는 점을 악용하여, 입력으로 명령의 의미를 바꾸어 데이터베이스를 부정하게 조작하는 공격. 플레이스홀더를 사용하는 프리페어드 스테이트먼트가 근본적인 대책이다.

일본어 명칭: SQLインジェクション

SQL 인젝션(SQL Injection)은(는) 정보 보안 기초, 사이버 공격과 방어의 실무 등 2개 분야의 연습 문제 4개에 나와요.

분야: 정보 보안 기초

공격이 성립하는 구조

애플리케이션이 '… WHERE name = ''과 입력값과 '''를 문자열로 이어 붙여 SQL 문을 만들고 있으면, 입력에 포함된 따옴표로 문자열이 닫히고 그 뒤의 부분이 SQL 명령으로 해석되어 버립니다. 교과서에서 자주 쓰이는 ' OR '1'='1이라는 입력에서는 '또는 '1'과 '1'이 같다'는 항상 성립하는 조건이 덧붙여져 인증을 그냥 통과할 수 있게 됩니다. 데이터의 읽기, 변경, 삭제로도 이어질 우려가 있습니다.

근본적인 대책

근본적인 대책은 플레이스홀더를 사용하는 프리페어드 스테이트먼트(매개변수화 쿼리)입니다. SQL 문의 구조를 먼저 확정하고 입력은 나중에 값으로만 결합하므로, 어떤 문자가 포함되어 있어도 명령의 일부가 되지 않습니다. 많은 프로그래밍 언어의 데이터베이스용 라이브러리나 프레임워크가 이 기능을 가지고 있습니다. 입력에서 특수 문자를 제거하는 방법은 누락이 생기기 쉽고, 브라우저 쪽의 입력 검사는 공격자가 우회하므로, 그것만으로는 대책이 되지 않습니다.

피해를 줄이는 대책

근본적인 대책에 더해, 애플리케이션이 데이터베이스에 접속하는 계정의 권한을 필요 최소한으로 하고(최소 권한의 원칙), 자세한 오류 메시지를 이용자에게 표시하지 않으며, WAF(웹 애플리케이션 방화벽)로 전형적인 공격 문자열을 탐지하는 등의 대책을 겹쳐 둡니다. WAF는 어디까지나 보조이며, 애플리케이션 수정을 대신하지는 못합니다.

  2. B브라우저 쪽에서 입력 문자의 종류를 확인하므로 서버에 부정한 문자열이 도달하지 않게 되기 때문에
  3. CSQL 문의 구조를 먼저 확정하고 입력은 나중에 값으로만 넘기므로, 입력에 어떤 문자가 포함되어 있어도 명령의 일부로 해석되지 않기 때문에

정답: C. SQL 문의 구조를 먼저 확정하고 입력은 나중에 값으로만 넘기므로, 입력에 어떤 문자가 포함되어 있어도 명령의 일부로 해석되지 않기 때문에

프리페어드 스테이트먼트에서는 먼저 'SELECT … WHERE id = ? AND password = ?'처럼 값 부분을 기호(플레이스홀더)로 한 SQL 문을 데이터베이스에 넘겨 구조를 확정하고, 그 후에 입력을 값으로만 결합합니다(바인드). 입력은 처음부터 끝까지 데이터로 취급되므로, 따옴표 등이 포함되어 있어도 조건을 덧붙이는 것 같은 명령의 일부가 되지 않습니다. 입력에서 위험한 문자를 제거하거나 이스케이프하는 방법은 데이터베이스의 종류나 문자 코드마다 다른 세세한 규칙을 빠짐없이 다루어야 하며, 한 곳이라도 빠지면 공격이 성립합니다. 또한 브라우저 쪽의 입력 검사는 공격자가 브라우저를 거치지 않고 직접 요청을 보내면 우회되므로, 편의를 위한 것이지 보안 대책은 되지 않습니다. 여기에 더해 데이터베이스에 접속하는 계정의 권한을 최소로 해 두면 피해를 줄일 수 있습니다.

자주 묻는 질문

SQL 인젝션은 이스케이프 처리로 막을 수 있나요?

이스케이프 처리로도 막을 수 있는 경우는 있지만, 데이터베이스의 종류나 문자 코드마다 다른 규칙을 빠짐없이 다루어야 하며, 한 곳이라도 빠지면 공격이 성립합니다. 그래서 플레이스홀더를 사용하는 프리페어드 스테이트먼트를 기본 대책으로 합니다.

입력 글자 수를 제한하면 SQL 인젝션을 막을 수 있나요?

막을 수 없습니다. 짧은 문자열로도 명령의 의미를 바꿀 수 있는 경우가 있습니다. 글자 수나 문자 종류의 제한은 보조적인 대책이며, 근본적인 대책은 프리페어드 스테이트먼트입니다.
