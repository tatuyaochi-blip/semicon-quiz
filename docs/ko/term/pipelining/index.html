파이프라인 처리(Pipelining)란?

명령 처리를 인출·해독·실행 등의 단계로 나누어, 여러 명령을 조금씩 어긋나게 동시에 처리하는 방식.

일본어 명칭: パイプライン処理

파이프라인 처리(Pipelining)은(는) CPU와 아키텍처, DRAM 등 2개 분야의 연습 문제 2개에 나와요.

분야: CPU와 아키텍처

파이프라인이 처리량을 높이는 방법

파이프라인은 조립 라인처럼 명령어 처리를 레지스터로 구분된 단계로 나눕니다. 고전적인 5단 RISC 파이프라인은 명령어 인출, 해독 및 레지스터 읽기, 실행, 메모리 접근, 라이트백 단계를 사용합니다. 한 명령어가 실행되는 동안 다음 명령어가 해독되고 세 번째 명령어가 인출되므로, 이상적으로는 클록마다 명령어 하나가 완료되어 처리량이 파이프라인이 없는 설계의 5배에 가까워집니다. 개별 명령어의 지연 시간은 줄지 않으며, 모든 명령어가 이제 모든 파이프라인 레지스터를 거치므로 오히려 약간 늘어납니다.

속도 향상이 기대에 못 미치는 이유

클록 주기는 가장 느린 단계에 레지스터 오버헤드, 즉 클록-Q 지연, 셋업 시간, 클록 스큐를 더한 값을 감당해야 합니다. 논리를 균등하게 나눌 수 없으면 가장 긴 단계가 주파수를 정하고, 다른 단계는 각 사이클의 일부 동안 놀게 됩니다. 파이프라인을 깊게 하면 각 단계가 짧아지지만, 고정된 레지스터 오버헤드가 주기에서 차지하는 비율이 커지고, 부분적으로 처리된 명령어를 더 많이 버려야 하므로 분기 예측 실패 페널티도 커집니다. 어느 지점을 넘으면 단계를 추가할수록 성능이 떨어지고 전력이 늘어나므로, 파이프라인 깊이는 균형을 맞춰 정하는 설계 선택입니다.

해저드와 그 처리

세 종류의 해저드가 이상적인 흐름을 방해합니다. 구조적 해저드는 두 명령어가 같은 사이클에 같은 자원을 필요로 할 때 생깁니다. 데이터 해저드는 명령어가 아직 기록되지 않은 결과를 필요로 할 때 생기며, 포워딩(바이패싱)으로 뒤쪽 단계의 결과를 직접 전달하지만, 고전적인 파이프라인에서는 로드 직후에 그 값을 사용하면 여전히 보통 1사이클의 스톨이 발생합니다. 제어 해저드는 인출 후 몇 단계가 지나야 결과를 알 수 있는 분기에서 생기며, 분기 예측으로 경로를 추측하고 예측이 빗나가면 잘못된 명령어를 플러시합니다.

CPU 밖의 파이프라인 처리

명령어 길이가 일정하고 로드/스토어 아키텍처를 갖는 RISC 명령어 집합은 깔끔하게 파이프라인화되도록 설계되었으며, x86 프로세서는 복잡한 명령어를 단순한 마이크로 연산으로 분해하여 비슷한 동작을 얻습니다. 같은 발상은 모든 동기식 데이터패스에 적용됩니다. 레지스터를 삽입하여 긴 임계 경로를 나누면 지연 시간을 대가로 최대 클록 주파수가 올라가며, 고위 합성 툴은 이를 파이프라인화 옵션으로 제공합니다. 소프트웨어 파이프라이닝은 컴파일러 측의 대응물로, 루프의 서로 다른 반복을 겹쳐 로드, 연산, 스토어가 병렬로 진행되게 하며, 루프 앞뒤에 프롤로그와 에필로그 코드를 둡니다.

CPU의 파이프라인 처리의 주된 목적으로 올바른 것은?

  1. A명령어 처리를 여러 단계로 나누고 서로 다른 명령어의 단계를 겹쳐 실행함으로써 처리량(스루풋)을 높인다
  2. B하나의 명령어 실행 시간(레이턴시)을 반드시 단축한다
  3. C명령어 수를 줄여 프로그램을 작게 만든다
정답과 해설 보기

정답: A. 명령어 처리를 여러 단계로 나누고 서로 다른 명령어의 단계를 겹쳐 실행함으로써 처리량(스루풋)을 높인다

파이프라인은 명령어의 인출, 해독, 실행, 메모리 접근, 쓰기 등의 단계를 조립 라인처럼 겹쳐서 매 클록 1개의 명령어를 완료시켜 처리량을 높입니다. 5단이라면 이상적으로는 약 5배입니다. 명령어 하나의 처리 시간(레이턴시)은 오히려 조금 늘어납니다. 데이터 의존, 분기, 자원 경합으로 흐름이 흐트러지는 것(해저드)이 있으며, 포워딩과 분기 예측으로 대처합니다.

자주 묻는 질문

파이프라인 처리를 하면 명령어 지연 시간이 줄어드나요?

아닙니다. 파이프라인은 명령어를 겹쳐 처리량을 높이지만, 각 명령어는 여전히 모든 단계를 거치며 레지스터 오버헤드 때문에 보통 약간 더 오래 걸립니다.

파이프라인 해저드 세 가지 종류

자원 충돌에 의한 구조적 해저드, 아직 사용할 수 없는 결과에 대한 의존에 의한 데이터 해저드, 분기에 의한 제어 해저드입니다. 대표적인 대책은 자원 이중화, 포워딩, 분기 예측입니다.

파이프라인을 최대한 깊게 하지 않는 이유

단계의 논리는 줄어드는데 레지스터 오버헤드는 고정되어 있어 이득이 점점 줄고, 깊은 파이프라인일수록 분기 예측 실패로 낭비되는 작업이 많아집니다. 전력과 설계 복잡도도 늘어납니다.

해설 속 파이프라인 처리(Pipelining)
