시스템 콜(system call)란?

애플리케이션이 파일 읽기·쓰기나 메모리 할당 등을 OS에 요청하는 구조. 전용 명령으로 예외를 일으켜 특권 모드로 전환하고 커널 처리를 호출한다.

일본어 명칭: システムコール

시스템 콜(system call)은(는) OS와 하드웨어, ISA와 어셈블리, 링커, 로더, 실행 파일 등 4개 분야의 연습 문제 11개에 나와요.

분야: OS와 하드웨어

시스템 콜의 단계별 흐름

RISC-V Linux에서는 프로그램이 시스템 콜 번호를 레지스터 a7에, 인수를 a0부터 차례로 넣은 뒤 ecall을 실행합니다. 이 명령어는 의도적으로 예외를 발생시키며, CPU는 ecall의 주소를 기록하고 슈퍼바이저 모드로 전환해 커널의 트랩 진입점으로 점프합니다. 커널은 사용자 레지스터를 저장하고, 번호로 핸들러를 찾아 인수를 검사한 뒤 처리를 수행하고 결과를 a0에 넣습니다. 그런 다음 저장된 주소를 ecall 다음으로 진행시키고 sret으로 사용자 모드로 복귀합니다. 다른 아키텍처에서는 x86-64의 syscall, Arm의 svc 같은 명령어를 사용합니다.

시스템 콜과 라이브러리 함수의 차이

프로그램은 보통 라이브러리 래퍼를 통해 시스템 콜을 호출하므로 경계를 놓치기 쉽습니다. printf 같은 함수는 전부 사용자 공간에서 실행되어 텍스트를 버퍼에 포맷하며, 가끔씩만 write 시스템 콜을 호출해 그 버퍼를 커널에 넘깁니다. 문자열 처리나 수학 루틴 같은 많은 라이브러리 함수는 커널에 전혀 들어가지 않습니다. 시스템 콜인지 여부는 함수 이름이 아니라 특권 모드로의 전환 여부로 정해집니다.

시스템 콜에 시간이 걸리는 이유

호출마다 모드 전환, 레지스터 저장과 복원, 인수 검증, 복귀라는 고정 오버헤드가 듭니다. 커널에 진입하면 캐시와 TLB도 교란되며, 커널 페이지 테이블 격리(KPTI) 같은 투기적 실행 공격 대책은 진입할 때마다 페이지 테이블 전환을 추가합니다. 따라서 호출 한 번에 1바이트씩 쓰면, 사용자 공간에서 수 KB를 버퍼링해 한 번의 호출로 쓰는 것보다 훨씬 느립니다.

호출을 줄이는 방법

버퍼링 외에도 mmap으로 파일을 메모리에 매핑할 수 있습니다. 그러면 읽기는 일반 로드가 되어, 읽을 때마다 호출하는 대신 처음 접근할 때의 페이지 폴트로 처리됩니다. 한 번의 호출로 여러 작업을 제출하는 인터페이스는 경계 통과를 더 줄여 줍니다. 일부 운영체제는 현재 시각 같은 읽기 전용 커널 데이터를 사용자 공간에 매핑해, 자주 하는 조회에 트랩이 전혀 필요 없게 하기도 합니다.

시스템 콜에서는 사용자 모드에서 특권 모드로의 전환, 레지스터 저장, 인수 확인, 복귀 처리 등이 매번 필요하며, 처리하는 양이 1바이트여도 이 고정 부담이 듭니다. 또한 커널에 진입하면 캐시나 TLB의 내용도 흐트러집니다. 버퍼에 모아 수 KB씩 한꺼번에 쓰면 시스템 콜 횟수가 크게 줄어 전체가 빨라집니다. 기록하는 데이터의 총량은 변하지 않으며, 결국에는 디스크에 기록됩니다.

시스템 콜과 인터럽트 차이

시스템 콜은 프로그램이 전용 명령어로 의도적으로 일으키는 동기적 트랩입니다. 인터럽트는 타이머나 장치 같은 하드웨어로부터 오는 비동기 신호로, 프로그램이 무엇을 하고 있든 상관없이 도착합니다.

printf는 시스템 콜인가요

아닙니다. printf는 사용자 공간에서 출력을 포맷하는 C 라이브러리 함수이며, 최종적으로 write 시스템 콜을 호출해 버퍼링된 데이터를 커널에 넘깁니다.

시스템 콜이 느린 이유

호출할 때마다 특권 모드로 전환하고 상태를 저장하며 인수를 검증하고 복귀해야 하고, 캐시와 TLB도 교란되기 때문입니다. 비용이 호출당 고정이므로 작은 호출이 많으면 누적됩니다.
