인터럽트 핸들러란?

인터럽트나 예외가 발생했을 때 CPU가 실행하는 처리. 중단된 처리의 상태를 저장하고 원인에 맞는 처리를 한 뒤 원래 처리로 돌아간다. 처리는 가능한 한 짧게 하는 것이 원칙.

일본어 명칭: 割り込みハンドラ

인터럽트 핸들러은(는) OS와 하드웨어, 임베디드 시스템과 펌웨어, CPU와 아키텍처 등 5개 분야의 연습 문제 11개에 나와요.

분야: OS와 하드웨어

인터럽트가 받아들여질 때 일어나는 일

장치가 인터럽트를 알리면 CPU는 현재 명령어를 끝내고, 다음에 실행했을 주소와 동작 모드, 플래그 같은 상태를 저장한 뒤, 보통 인터럽트 벡터 테이블을 통해 찾은 인터럽트 핸들러로 점프합니다. 인터럽트 핸들러는 인터럽트 서비스 루틴(ISR)이라고도 합니다. 핸들러는 자신이 사용할 레지스터를 저장하고, 원인을 처리하고, 장치의 인터럽트 플래그를 지우고, 상태를 복원한 뒤 인터럽트 복귀 명령을 실행합니다. 그러면 중단된 프로그램은 멈춘 지점에서 정확히 재개되며, 버려지거나 처음부터 다시 시작되지 않습니다.

핸들러를 짧게 해야 하는 이유

핸들러가 실행되는 동안에는 보통 같거나 낮은 우선순위의 다른 인터럽트가 보류되고 메인 코드도 멈추므로, 핸들러가 길면 다른 모든 처리의 지연이 늘어납니다. printf처럼 느린 호출은 시간이 걸리고 그 자체가 인터럽트에 의존할 수도 있어 특히 위험합니다. 좋은 핸들러는 수신 데이터를 버퍼로 옮기거나 플래그를 세우는 등 최소한의 일만 하고, 무거운 처리는 메인 루프나 태스크에 맡깁니다. 운영 체제 커널은 작업을 즉시 처리하는 부분과 지연 처리하는 부분으로 나누어 이를 체계화합니다.

메인 코드와의 데이터 공유

핸들러와 메인 프로그램이 공유하는 변수는 고전적인 버그의 원인이 됩니다. 메인이 핸들러만 설정하는 플래그를 반복해서 확인할 때, 최적화 컴파일러는 그 값을 한 번만 레지스터에 읽어 들이고 갱신을 영영 보지 못할 수 있습니다. volatile로 선언하면 모든 접근이 메모리를 거치도록 강제됩니다. reg |= mask 같은 읽기-수정-쓰기는 읽기와 쓰기 사이에 인터럽트될 수 있어, 핸들러가 다른 비트에 가한 변경을 지워 버릴 수 있습니다. 인터럽트를 잠시 금지하거나 하드웨어의 세트/클리어 레지스터를 사용하면 이를 피할 수 있으며, 여러 바이트로 된 변수는 일부만 갱신된 값을 읽지 않도록 보호해야 합니다.

스케줄링과 워치독에서의 인터럽트

주기적인 타이머 인터럽트는 CPU를 양보하지 않는 프로그램으로부터 운영 체제가 CPU를 되찾을 수 있게 해 주며, 이를 통해 선점형 스케줄링과 컨텍스트 스위치가 가능해집니다. 인터럽트는 하드웨어에서 오는 비동기 사건이고, 페이지 폴트나 0으로 나누기 같은 예외는 실행 중인 명령어에서 동기적으로 발생하지만, 둘 다 비슷한 핸들러를 통해 커널에 진입합니다. 흔한 실수 하나는 타이머 인터럽트 안에서 워치독 타이머를 무조건 리셋하는 것입니다. 메인 루프가 멈춰도 인터럽트는 계속 발생하므로 워치독이 고장을 결코 감지하지 못합니다.

  3. C인터럽트를 막는 시간을 짧게 하고 무거운 처리를 나중에 수행하기 위해

정답: C. 인터럽트를 막는 시간을 짧게 하고 무거운 처리를 나중에 수행하기 위해

인터럽트 핸들러 실행 중에는 같은 종류나 더 낮은 우선순위의 인터럽트가 대기하는 경우가 많아, 긴 처리를 하면 시스템 전체의 응답이 나빠집니다. 그래서 장치에서 상태를 읽어 접수를 알리는 등 급한 처리만 먼저 하고, 데이터 가공이나 상위로의 통지 같은 시간이 걸리는 처리는 나중에 인터럽트를 허용한 일반 컨텍스트에서 수행합니다. 처리 총량은 줄지 않으며 후반부도 소프트웨어가 수행합니다.

메인 처리에서 레지스터 비트를 'reg |= mask;'(읽기-수정-쓰기)로 조작하는 도중에 인터럽트 핸들러가 같은 레지스터의 다른 비트를 바꾸면 발생할 수 있는 문제와 대책의 조합으로 올바른 것은 무엇입니까?

  1. A인터럽트에서 한 변경이 메인 처리의 되쓰기로 사라진다. 조작하는 동안만 인터럽트를 금지하거나, 비트별 세트·클리어 전용 레지스터를 사용한다
  2. B레지스터가 망가져 다시는 사용할 수 없게 된다. 마이크로컨트롤러를 교체한다
  3. C아무 일도 일어나지 않는다. 대책은 필요 없다
정답과 해설 보기

정답: A. 인터럽트에서 한 변경이 메인 처리의 되쓰기로 사라진다. 조작하는 동안만 인터럽트를 금지하거나, 비트별 세트·클리어 전용 레지스터를 사용한다

'reg |= mask'는 레지스터를 읽고, OR를 취하고, 되쓰는 세 가지 동작입니다. 읽은 직후에 인터럽트가 들어와 핸들러가 다른 비트를 바꿔도, 메인 처리는 인터럽트 이전에 읽은 오래된 값을 바탕으로 되쓰기 때문에 핸들러의 변경이 사라집니다. 조작하는 동안만 인터럽트를 금지하거나, 1을 쓴 비트만 바뀌는 세트용·클리어용 레지스터를 사용하면 한 번의 쓰기로 끝나므로 이 문제는 발생하지 않습니다.

자주 묻는 질문

인터럽트 핸들러와 ISR의 차이는 무엇인가요?

실질적인 차이는 없습니다. 인터럽트 서비스 루틴(ISR)은 인터럽트에 대응해 CPU가 실행하는 코드인 인터럽트 핸들러의 다른 이름입니다.

인터럽트 핸들러와 공유하는 변수는 왜 volatile로 선언해야 하나요?

volatile이 없으면 컴파일러가 루프 안에서 그 변수가 바뀌지 않는다고 가정하고 레지스터에 보관할 수 있어, 메인 코드가 핸들러의 갱신을 보지 못합니다. volatile은 모든 접근이 메모리를 읽거나 쓰도록 강제합니다.

인터럽트와 예외의 차이는 무엇인가요?

인터럽트는 타이머나 주변 장치 같은 하드웨어에서 오는 비동기 신호로, 현재 명령어와 관계가 없습니다. 예외는 페이지 폴트나 잘못된 연산처럼 실행 중인 명령어에 의해 동기적으로 발생합니다.
