SystemVerilogとは

しすてむべりろぐ

Verilogを拡張した言語。logic型やalways_ff・always_combなどの設計の機能と、クラス、制約付きランダム、アサーションなどの検証の機能を持つ。

「SystemVerilog」は、2分野の10問の練習問題に出てきます(ハードウェア記述言語と検証, LSI設計フロー・EDAなど)。

この用語の分野: ハードウェア記述言語と検証

設計のためにSystemVerilogが加えた機能

SystemVerilogはIEEE 1800として標準化された、Verilogの上位互換の言語で、ハードウェアを書くための機能と検証するための機能の両方を追加しています。設計面では、ドライバが1つの信号について、わかりにくかったVerilogのwireとregの区別をlogic型が置き換えます。always_ff、always_comb、always_latchは意図するハードウェアを明示し、enum、struct、パッケージ、インタフェースはRTLを読みやすく、誤りにくくします。Verilogのregは、単にalwaysブロックで代入される信号という意味で、フリップフロップとは限りません。トライステートバスのようにドライバが複数ある信号には今でもwireを使い、logicはXやZも保持できる4値の型です。

RTLの誤りを早く見つける

Verilogでよくあるバグが、意図しないラッチです。組み合わせ回路のalwaysブロックで、ある経路で出力に代入していないと、ツールは古い値を記憶せざるを得なくなります。定番の対策は、ブロックの先頭ですべての出力に既定値を代入することです。always_combを使えば、ツールは組み合わせ回路が意図されていることもわかるので、ラッチが推論されると警告やエラーを出します。また、センシティビティリストは読まれる信号から自動的に作られるので、手書きのリストで信号を書き漏らす誤りも防げます。always_ffも同様に、エッジトリガのフリップフロップに対応しないコードを指摘します。

検証のための機能

SystemVerilogの追加機能の大半はテストベンチ向けです。クラスはオブジェクト指向プログラミングを可能にし、制約付きランダム生成は、ワード境界にそろったアドレスや1〜256の長さのような正当な刺激を作ります。カバーグループは機能カバレッジを測定し、どのケースを試したかを示します。SystemVerilogアサーション(SVA)は、要求から3サイクル以内に応答があるといった時間的な性質を表現し、シミュレーションで確認したり形式検証ツールで証明したりします。クロッキングブロックはテストベンチの信号を駆動・サンプリングするタイミングを定め、設計との競合を防ぎます。UVM(Universal Verification Methodology、IEEE 1800.2)は、これらの機能の上に再利用可能なテストベンチを構築します。

合成できるコードとテストベンチ専用のコード

SystemVerilogのうち、ハードウェアを記述するのは一部だけです。logic、always_ff、always_comb、enum、struct、パッケージ、インタフェースなどを含む合成可能なサブセットは、論理合成ツールが受け付けてゲートになります。クラス、ランダム化、カバレッジ、そして動的なデータ型の多くはシミュレーションの中にだけ存在し、設計を取り巻く環境を記述します。アサーションはRTLに結び付けて、シミュレーション、形式検証、場合によってはエミュレーションで使えますが、機能を持つ論理回路にはなりません。主な代替言語は今もVHDLで、特に一部のFPGAや航空宇宙分野のチームで使われています。

SystemVerilogの練習問題に挑戦

SystemVerilogを使った検証で、再利用しやすいテスト環境(テストベンチ)を組み立てるための標準的な方法論はどれか。

  1. AOPC
  2. BCMP
  3. CUVM(Universal Verification Methodology)
答えと解説を見る

正解：C. UVM(Universal Verification Methodology)

UVMは、SystemVerilogでテストベンチを部品(入力を与えるドライバ、出力を監視するモニタ、期待値と比べるスコアボードなど)の組み合わせとして構成するための標準的な方法論とクラスライブラリです。部品を他の設計の検証にも再利用でき、制約付きランダムな入力の生成やカバレッジの収集を組み込みやすくなります。IEEE 1800.2として標準化されています。OPCとCMPは製造の技術です。

SystemVerilogの制約付きランダム検証の説明として正しいものはどれか。

  1. A入力の値を、仕様で許される範囲や組み合わせの条件(制約)の中でランダムに作り、人が思いつかない場合も含めて広く試す
  2. B入力の値を完全にでたらめに作り、仕様にない値も多く与える
  3. C入力の値を人がすべて手で書く
答えと解説を見る

正解：A. 入力の値を、仕様で許される範囲や組み合わせの条件(制約)の中でランダムに作り、人が思いつかない場合も含めて広く試す

人が考えたテスト(指定型のテスト)だけでは、設計者が想定しなかった組み合わせの不具合を見逃しがちです。制約付きランダム検証では、例えば「アドレスは4の倍数」「長さは1〜256」のような制約を書き、その中でランダムに入力を作るので、意味のある入力だけで多くの場合を試せます。どの場合を試せたかはカバレッジで測り、足りない部分は制約を変えたり指定型のテストで補ったりします。

よくある質問

VerilogとSystemVerilogの違いは?

SystemVerilogはVerilogの上位互換で、logic、always_ff、always_combといったより安全な設計用の構文と、クラス、制約付きランダム刺激、機能カバレッジ、アサーションといった検証機能を追加しています。既存のVerilogのコードは、一般にそのままSystemVerilogとしても有効です。

SystemVerilogは論理合成できますか?

logic、always_ff、always_comb、struct、enum、インタフェースなどを含む設計用のサブセットは合成できます。クラス、ランダム化、カバーグループといった検証用の構文はシミュレーション専用です。

wireとregの代わりにlogicを使うべきですか?

ドライバが1つの信号なら、logicはassign文で駆動してもalwaysブロックで駆動しても使えるので、ほとんどのコードでwireとregの両方を置き換えられます。トライステートバスのようにドライバが複数あるネットにはwireを使います。

「SystemVerilog」が出てくる問題(10問)

  1. SystemVerilogを使った検証で、再利用しやすいテスト環境(テストベンチ)を組み立てるための標準的な方法論はどれか。
  2. SystemVerilogの制約付きランダム検証の説明として正しいものはどれか。
  3. SystemVerilogのlogic型の利点として正しいものはどれか。
  4. SystemVerilogのalways_ffやalways_combを、Verilogのalwaysの代わりに使う利点として正しいものはどれか。
  5. RTL設計で主に使われるハードウェア記述言語はどれか。
  6. 設計が満たすべき性質(例えば「要求が来たら3サイクル以内に応答する」)を記述しておき、シミュレーション中や形式検証で自動的にチェックさせる手法はどれか。
  7. Verilogのwire型とreg型の違いとして正しいものはどれか。
  8. Verilogで「always @(*)」と書く意味として正しいものはどれか。
  9. 組み合わせ回路のalwaysブロックで、意図しないラッチを防ぐためによく使われる書き方はどれか。
