ABA問題とは

えーびーえーもんだい

値がAからBに変わってまたAに戻ったとき、値だけを比べるCASが変化に気づかずに成功してしまう問題。ロックフリーのデータ構造で注意が必要。

「ABA問題」は、1分野の2問の練習問題に出てきます(マルチコアと同期など)。

この用語の分野: マルチコアと同期

ABA問題が起きる仕組み

コンペアアンドスワップ(CAS)は、ある場所がまだ期待した値を保持している場合にだけ新しい値を書き込む操作で、比べるのは値であって履歴ではありません。先頭(head)がノードAを指し、AのnextポインタがノードBを指しているロックフリーのスタックを考えます。スレッド1がhead = Aとnext = Bを読んだところで中断されます。スレッド2がAとBをポップし、Aをプッシュし直すか、たまたまAと同じアドレスを再利用した新しいノードをプッシュします。スレッド1が再開すると、headはまだAなのでCAS(head, A, B)は成功し、headはもはやスタックにないノードBを指してしまいます。

メモリの再利用で起きやすくなる理由

この問題は、メモリを手動で管理する言語で特によく起こります。ノードを解放すると、アロケータは次の割り当てで同じアドレスをすぐに渡すので、別のノードを指していてもポインタの値がAに戻ることがあります。ガベージコレクションのある言語では、スレッドが参照を保持している間はノードが回収されないため、アドレスの再利用によるABAはほぼ起きません。ただし、同じノードを意図的に再挿入した場合には、論理的なABAが起こりえます。

代表的な対策

古典的な対策は、ポインタに更新カウンタを組み合わせ、倍幅のCASやポインタの空きビットを使って両方を1回のアトミック操作で比較することです。更新のたびにカウンタを増やすので、タグ5のAとタグ7のAは別のものとして区別されます。ロードリンク/ストアコンディショナル(LL/SC、RISC-VではLR/SC)は、ロード以降にその場所へ少しでも書き込みがあれば、値が同じでも失敗します。ハザードポインタやエポックベースの回収といった安全なメモリ回収の手法は、どこかのスレッドがまだアクセスする可能性がある間、ノードが解放・再利用されないようにします。

ABAとロックフリーの進行保証

ロックフリーのアルゴリズムは、ほかのスレッドが止まっても、常にどれかのスレッドが前に進むことを保証します。CASが失敗するのは、ほかのスレッドの更新が成功したときだけだからです。しかし、この進行保証は正しさについては何も保証しません。ABAは、一見正しいCASのループがデータ構造を壊してしまう典型例です。特定の実行の重なり方とメモリの再利用がそろわないと起きないため、テストで見つけるのは困難です。ロックフリーのコードは、最初からABAへの対策を明確に組み込んで設計すべきです。

ABA問題の練習問題に挑戦

CASを使ったロックフリーのデータ構造で問題になるABA問題の説明として正しいものはどれか。

  1. AAとBの2つのスレッドが、交互にしか実行できなくなる
  2. B値がAからBに変わり、またAに戻ったとき、CASは変化に気づかずに成功してしまう
  3. CAとBの2つのロックを、逆の順番で取ってしまう
答えと解説を見る

正解：B. 値がAからBに変わり、またAに戻ったとき、CASは変化に気づかずに成功してしまう

連結リストの先頭のポインタがAのとき、あるスレッドがAを読んでCASの準備をする間に、ほかのスレッドがAを取り除き、Bの操作をして、再び同じ番地Aのノードを入れることがあります。CASは値がAのままなので成功しますが、リストの中身はすでに変わっていて、構造が壊れます。ポインタに更新回数を添えて一緒に比べる方法や、LR/SCを使う方法で防ぎます。

よくある質問

ABA問題とは、簡単に言うと何ですか?

あるスレッドが値Aを読んだ後、別のスレッドがそれをBに変えてからAに戻すと、最初のスレッドのCASが何事もなかったかのように成功してしまう問題です。値は一致していても、その背後の状態は変わっています。

LL/SCはどのようにABA問題を避けますか?

ストアコンディショナルは、対応するロードリンク以降にその場所への書き込みが一度もなかった場合にだけ成功し、書き込まれた値は関係ありません。そのため、AからBに変わってAに戻った場合でもストアは失敗します。

バージョンカウンタでABA問題は完全に解決しますか?

スレッドが止まっている間にカウンタが一周して同じ値に戻らないだけの幅があれば、実用上は解決します。カウンタの幅が非常に狭いと、理論上は一周して問題が再発する可能性があります。
