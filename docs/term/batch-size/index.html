バッチサイズとは

ばっちさいず

まとめて処理する入力の数。大きくすると重みを再利用できて効率が上がるが、応答の遅れとメモリが増える。

「バッチサイズ」は、1分野の4問の練習問題に出てきます(AIハードウェアとソフトウェアスタックなど)。

この用語の分野: AIハードウェアとソフトウェアスタック

バッチ処理で効率が上がる理由

ニューラルネットワークの層では、重みはどの入力に対しても同じです。バッチサイズ1では、全結合層は行列ベクトル積となり、各重みはメモリから読み出されても1回の積和演算にしか使われません。演算強度はFP16で約1 FLOP/バイトとなり、演算器はほとんどメモリを待つことになります。バッチサイズをBにすると層は行列同士の積となり、重みのトラフィックは変わらないまま演算がB倍になるので、演算強度もおよそB倍になり、処理はメモリ律速から演算律速の側へ移ります。サーバは多数のユーザからの要求をまとめることで、この性質を利用しています。

遅延とメモリのコスト

バッチを大きくすると全体のスループットは上がりますが、個々の速度は上がりません。他の要求がそろうのを待つことがあり、1バッチの計算にも時間がかかるため、要求ごとの遅延は大きくなります。対話型のサービスでは、応答時間の目標が許す範囲でしかバッチを大きくしません。メモリも増えます。LLM(大規模言語モデル)の推論では、過去のトークンのアテンションのキーとバリューを再計算しないよう保存するKVキャッシュが、層数、キーとバリューの次元、トークン数、バッチサイズ、要素あたりのバイト数に比例して増えます。長いコンテキストや多数の要求では数十GBに達し、重みより大きくなることもあります。

LLMのデコードでの具体的な数値

バッチサイズ1のデコードでは、トークンを1つ生成するたびにすべての重みを読み出す必要があります。そのため、FP16で約14 GBの重みを持つモデルを帯域2 TB/sのGPUで動かすと、1トークンに少なくとも14 GB ÷ 2 TB/s = 7 msかかり、毎秒約140トークンが上限です。重みを4ビットに量子化して約3.5 GBにすれば、この下限は約1.75 msに下がります。バッチを大きくすると重みを1回読むごとに複数のトークンを生成でき、演算性能かKVキャッシュのメモリが制約になるまで全体のスループットが何倍にもなります。KVキャッシュの圧迫は、キャッシュの低精度化、ヘッド間でのキーとバリューの共有、ブロック単位のメモリ管理で緩和できます。

学習におけるバッチサイズ

学習でのバッチ(ミニバッチ)は、1回の重み更新のために勾配を平均するサンプルの集まりです。バッチを大きくするとハードウェアを効率よく使え、データ全体を1周する(1エポック)のに必要な更新ステップも減ります。ただし、逆伝播のための活性値のメモリはバッチサイズとモデルの深さに応じて増えます。これに対処するのが勾配チェックポイントで、一部の活性値だけを保存し、残りを順伝播およそ1回分の追加計算で再計算します。バッチサイズを大きく変えると勾配のノイズが変わるため、通常は学習率の調整し直しが必要になります。

バッチサイズの練習問題に挑戦

入力が1つだけ(バッチサイズ1)のとき、全結合層の計算(重みの行列とベクトルの積)がメモリ律速になりやすい理由として正しいものはどれか。

  1. Aベクトルの要素の数が多すぎて、演算器に入りきらないから
  2. B行列とベクトルの積は、GPUでは計算できないから
  3. C重みの各要素をメモリから読んでも、1回の積和にしか使わないので、演算強度が非常に低いから
答えと解説を見る

正解：C. 重みの各要素をメモリから読んでも、1回の積和にしか使わないので、演算強度が非常に低いから

行列とベクトルの積では、重みの行列の各要素を1回読んで、入力の1つの要素と1回掛けて足すだけです。FP16なら2バイトにつき2回の演算で、演算強度は約1です。重みの読み込みに時間がかかり、演算器はほとんど待っています。同じ重みを複数の入力に使えるように入力をまとめる(バッチを大きくする)と、演算強度が上がります。

推論でバッチサイズ(まとめて処理する入力の数)を大きくすると、処理全体の効率が上がりやすい理由はどれか。

  1. A入力が多いほど、1つの入力の計算の回数が減るから
  2. Bバッチを大きくすると、重みの数が減るから
  3. C一度読み込んだ重みを複数の入力の計算に使えるので演算強度が上がり、演算器を有効に使えるから
答えと解説を見る

正解：C. 一度読み込んだ重みを複数の入力の計算に使えるので演算強度が上がり、演算器を有効に使えるから

バッチサイズがBなら、重みの行列とB個のベクトルの積は、重みの行列と幅Bの行列の積になります。重みの読み込みは同じなのに演算はB倍になるので、演算強度もおよそB倍になり、メモリ律速から演算律速に近づきます。サーバでの推論では、多くの利用者の要求をまとめて処理することで、GPUを効率よく使っています。

よくある質問

バッチサイズを大きくすると推論は速くなりますか?

重みを1回読むごとに処理できる入力が増えるので、全体のスループットは上がります。ただし個々の要求の待ち時間は通常長くなるため、遅延は悪化します。

バッチサイズを大きくするとGPUメモリの使用量が増えるのはなぜですか?

活性値やLLMのKVキャッシュは入力ごとに保持されるため、重みの量は変わらなくても、バッチサイズに比例して増えるからです。

バッチサイズとエポックの違いは?

バッチサイズは1ステップ(1回の重み更新)で処理するサンプル数で、エポックは学習データ全体を1周することです。1エポックには「データセットのサイズ ÷ バッチサイズ」回のステップがかかります。

解説の中の「バッチサイズ」

  • バッチサイズがBなら、重みの行列とB個のベクトルの積は、重みの行列と幅Bの行列の積になります。

    推論でバッチサイズ(まとめて処理する入力の数)を大きくすると、処理全体の効率が上がりやすい理由はどれか。

「バッチサイズ」が出てくる問題(4問)

  1. 入力が1つだけ(バッチサイズ1)のとき、全結合層の計算(重みの行列とベクトルの積)がメモリ律速になりやすい理由として正しいものはどれか。
  2. 推論でバッチサイズ(まとめて処理する入力の数)を大きくすると、処理全体の効率が上がりやすい理由はどれか。
  3. 推論でバッチサイズを大きくしすぎたときの欠点として正しいものはどれか。
  4. FP16で約14 GBの重みを持つモデルを、メモリ帯域2 TB/sのGPUでバッチサイズ1でデコードする。1トークンの生成にかかる時間の下限に最も近いものはどれか。
