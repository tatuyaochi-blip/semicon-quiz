偽共有とは

にせきょうゆう

別々のスレッドが別々の変数を書き換えているのに、それらが同じキャッシュラインにあるため、ラインがコア間を行き来して遅くなる現象。フォールスシェアリング。

「偽共有」は、2分野の4問の練習問題に出てきます(マルチコアと同期, CPU・アーキテクチャなど)。

この用語の分野: マルチコアと同期

コヒーレンスは変数単位ではなくライン単位

MESI(Modified、Exclusive、Shared、Invalid)などのキャッシュコヒーレンスプロトコルは、個々の変数ではなく、通常64 バイトのキャッシュライン全体を単位として所有権を管理します。コアが書き込むには、そのラインを排他的に保持する必要があり、そのとき他のすべてのコアにあるコピーは無効化されます。同じライン上で、コア0が変数aを、コア1が変数bを書き換え続けると、書き込みのたびにラインが2つのキャッシュの間を移動します。どちらのスレッドも相手のデータは読まないので結果は正しいままですが、本来なら数サイクルで済むL1ヒットが、遅いコア間転送に変わってしまいます。

偽共有と真の共有の違い

真の共有とは、グローバルなカウンタやロック変数のように、複数のスレッドが実際に同じ変数にアクセスすることです。この競合は本質的なもので、カウンタを分割するなどアルゴリズムを変えなければ解消できません。一方、偽共有ではデータは論理的に独立しており、たまたまメモリ上で隣り合っているだけなので、データ配置を変えれば解決します。どちらも、少数のラインにコヒーレンストラフィックが集中するという同じ症状を示します。読み出しだけの共有はどちらの問題も起こしません。多数のキャッシュが同時にラインをShared状態で保持でき、無効化を引き起こすのは書き込みだけだからです。

よくある原因

典型例は、スレッドごとのカウンタを並べた配列です。要素が8 バイトなら64 バイトのラインに8個入るため、最大8スレッドが1本のラインを奪い合います。ほかにも、異なるスレッドが別々のフィールドを更新する構造体、別のロックで保護されるデータと同じラインに置かれたロック、生産者と消費者がそれぞれ書き込むheadとtailのインデックスが隣り合ったワークキューなどがよく問題になります。各スレッドが自分のデータにしか触れていないように見えるのに、スレッドを増やしても速度向上が頭打ちになったり、かえって遅くなったりするのが典型的な兆候です。

対策と検出方法

独立して書き換えられるデータを、それぞれキャッシュラインサイズにパディングまたはアラインします。たとえばC/C++ではalignas(64)を使い、各スレッドが専用のラインを持つようにします。隣り合う2本のラインをまとめて取り込むプロセッサもあるため、128 バイト離す場合もあります。さらに良いのは、各スレッドがローカル変数やレジスタで集計し、最後に一度だけ共有領域へ書き込む方法です。問題の発見にはハードウェア性能カウンタが役立ちます。Linuxのperf c2cツールは、あるコアが頻繁に書き換え、別のコアがそれにアクセスしているキャッシュラインを報告します。

偽共有の練習問題に挑戦

マルチスレッドのプログラムで起こる偽共有(フォールスシェアリング)の説明として正しいものはどれか。

  1. A別々のスレッドが別々の変数を書き換えているのに、それらが同じキャッシュラインにあるため、ラインがコア間を行き来して遅くなる
  2. B2つのスレッドが同じ変数を同期せずに書き換えて、値が壊れる
  3. Cスレッドどうしが互いのロックを待ち合って、止まってしまう
答えと解説を見る

正解：A. 別々のスレッドが別々の変数を書き換えているのに、それらが同じキャッシュラインにあるため、ラインがコア間を行き来して遅くなる

コヒーレンシはキャッシュライン(一般に64バイト)の単位で管理されます。コア0が変数a、コア1が変数bを書き換えるだけでも、aとbが同じラインにあると、書き込むたびに相手のコピーが無効になり、ラインが2つのコアの間を行き来します。結果は正しいのに、性能が大きく落ちるのが偽共有です。スレッドごとの集計用の配列などで起こりやすい問題です。

スレッドごとのカウンタを「long cnt[8];」のように並べた配列で偽共有が起きている。対策として最も適切なものはどれか。

  1. Aカウンタの型をlongからintに変えて、配列を小さくする
  2. B各カウンタの間に詰め物を入れたり整列させたりして、別々のキャッシュラインに置く
  3. Cスレッドの数を増やして、待ち時間を分散させる
答えと解説を見る

正解：B. 各カウンタの間に詰め物を入れたり整列させたりして、別々のキャッシュラインに置く

longが8バイトなら、8個のカウンタは64バイトの1つのラインに収まり、全部のスレッドが同じラインを奪い合います。各カウンタを64バイトごとに置くように詰め物を入れるか、構造体をキャッシュラインの大きさに整列させれば、スレッドごとに別のラインを使えます。また、各スレッドは局所変数で数えて、最後に1回だけ共有の場所へ足す方法も効果的です。

よくある質問

偽共有が起きると計算結果が間違うことはありますか?

いいえ。コヒーレンスプロトコルがすべての変数を正しく保つため、結果は正しいままです。変数を含むキャッシュラインがコア間を行き来し続けることで、時間がかかるだけです。

偽共有を防ぐにはどれくらいパディングすればよいですか?

独立して書き込まれる変数がそれぞれ専用のキャッシュラインに収まるだけ、通常は64 バイトです。隣り合うラインのペアをまとめてプリフェッチするCPUがあるため、128 バイトにするコードもあります。

読み出し専用の共有データでも偽共有は起きますか?

起きません。複数のコアが同じラインを共有状態で同時に保持できるためです。問題になるのは、少なくとも1つのスレッドがそのラインに書き込む場合だけです。
