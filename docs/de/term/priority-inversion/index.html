Was ist Prioritätsinversion?

Phänomen, bei dem ein Task hoher Priorität auf eine von einem Task niedriger Priorität gehaltene Ressource wartet, während ein Task mittlerer Priorität den niedrigen verdrängt und weiterläuft, sodass der hohe lange warten muss.

Japanische Bezeichnung: 優先度逆転

Fachgebiet: Embedded Systems und Firmware

Wie Prioritätsinversion entsteht

Betrachten wir drei Tasks in einem präemptiven Echtzeitbetriebssystem (RTOS): hohe (H), mittlere (M) und niedrige (L) Priorität. L sperrt einen Mutex, der eine gemeinsame Ressource schützt. H wird lauffähig, braucht denselben Mutex und blockiert, bis L ihn freigibt. Nun wird M lauffähig, das mit der Ressource nichts zu tun hat. Da M eine höhere Priorität als L hat, führt der Scheduler M aus, und L kann die Stelle nicht erreichen, an der es den Mutex freigibt. Solange M läuft, wartet auch H; faktisch verzögert also ein Task mittlerer Priorität den Task höchster Priorität, und die beabsichtigte Reihenfolge kehrt sich um.

Begrenzte vs. unbegrenzte Inversion

Ein gewisses Blockieren ist unvermeidlich, sobald Tasks eine Ressource teilen: Hält L den Mutex, muss H warten, bis L seinen kritischen Abschnitt beendet hat. Diese Verzögerung ist durch die Länge des kritischen Abschnitts begrenzt und kann in die Zeitanalyse einbezogen werden. Das Problem ist die Störung durch mittlere Prioritäten, die die Verzögerung unbegrenzt macht, da beliebig viele mittlere Tasks dazwischen laufen können. In einem harten Echtzeitsystem, in dem Deadlines garantiert werden müssen, kann eine unbegrenzte Verzögerung eine verpasste Deadline, einen Watchdog-Reset oder unsicheres Verhalten bedeuten; deshalb erhält das Thema so viel Aufmerksamkeit.

Prioritätsvererbung und Priority Ceiling

Prioritätsvererbung (Priority Inheritance) löst das Problem dynamisch: Blockiert H an einem von L gehaltenen Mutex, übernimmt L vorübergehend die Priorität von H, sodass M es nicht verdrängen kann. L beendet seinen kritischen Abschnitt, gibt den Mutex frei, fällt auf seine eigene Priorität zurück, und H läuft. Viele RTOS-Mutexe bieten diese Option. Das Priority-Ceiling-Protokoll ist eine statische Alternative: Jedem Mutex wird die Priorität des höchsten Tasks zugewiesen, der ihn nutzen darf, und jeder Task, der ihn sperrt, wird sofort auf diese Obergrenze angehoben. Ceiling-Protokolle verhindern auch bestimmte Deadlocks, erfordern aber eine Analyse, welche Tasks welche Ressourcen nutzen.

Der Vorfall bei Mars Pathfinder

Ein bekanntes Beispiel ereignete sich 1997 beim Mars-Pathfinder-Lander. Nach der Landung kam es wiederholt zu System-Resets. Ein Task hoher Priorität wartete auf einen Mutex, den ein Task niedriger Priorität hielt, der wiederum von Arbeit mittlerer Priorität verdrängt wurde, bis ein Watchdog-Timer bemerkte, dass ein periodischer Task nicht rechtzeitig fertig geworden war, und das System zurücksetzte. Ingenieure reproduzierten das Problem an einem Nachbau am Boden und behoben es, indem sie die Prioritätsvererbung für den betroffenen Mutex aktivierten. Kritische Abschnitte kurz zu halten und möglichst wenige Ressourcen über Prioritätsebenen hinweg zu teilen, bleiben nützliche Entwurfsregeln.

Häufige Fragen

Was ist Prioritätsinversion in einem RTOS?

Eine Situation, in der ein Task hoher Priorität auf eine von einem Task niedriger Priorität gehaltene Ressource wartet und ein Task mittlerer Priorität den niedrigen verdrängt, sodass der Task hoher Priorität faktisch durch den mittleren verzögert wird. Die Verzögerung kann unbegrenzt werden.

Was ist der Unterschied zwischen Prioritätsvererbung und Priority Ceiling?

Prioritätsvererbung hebt die Priorität des Lock-Halters nur an, wenn ein Task höherer Priorität tatsächlich an diesem Lock blockiert. Priority Ceiling hebt jeden Task auf eine voreingestellte Obergrenze an, sobald er das Lock nimmt, was auch hilft, Deadlocks zu verhindern.

Wie wurde die Prioritätsinversion bei Mars Pathfinder behoben?

Die wiederholten Resets wurden auf eine Prioritätsinversion an einem gemeinsam genutzten Mutex zurückgeführt, und die Ingenieure behoben sie, indem sie in der Flugsoftware die Prioritätsvererbung für diesen Mutex aktivierten.
