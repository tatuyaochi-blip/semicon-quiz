Was ist False Sharing?

Phänomen, bei dem verschiedene Threads verschiedene Variablen beschreiben, diese aber in derselben Cache-Line liegen, sodass die Line zwischen den Kernen hin- und herwandert und die Ausführung langsamer wird.

Japanische Bezeichnung: 偽共有

„False Sharing“ kommt in 4 Übungsfragen aus 2 Themen vor, z. B. Multicore und Synchronisation, CPU und Architektur.

Fachgebiet: Multicore und Synchronisation

Warum Kohärenz pro Line statt pro Variable arbeitet

Cache-Kohärenzprotokolle wie MESI (Modified, Exclusive, Shared, Invalid) verfolgen den Besitz ganzer Cache-Lines, typischerweise 64 Byte, nicht einzelner Variablen. Bevor ein Kern schreiben kann, muss er die Line exklusiv halten, was die Kopien aller anderen Kerne invalidiert. Schreibt Kern 0 fortlaufend Variable a und Kern 1 fortlaufend Variable b in derselben Line, zwingt jeder Schreibvorgang die Line, zwischen den beiden Caches zu wandern. Keiner der Threads liest die Daten des anderen, sodass die Ergebnisse korrekt bleiben, aber ein Zugriff, der ein L1-Hit von wenigen Zyklen wäre, wird zu einer langsamen Übertragung zwischen Kernen.

False Sharing vs. True Sharing

True Sharing bedeutet, dass Threads wirklich auf dieselbe Variable zugreifen, etwa einen globalen Zähler oder ein Lock-Wort; der Konflikt ist inhärent und lässt sich nur durch eine Änderung des Algorithmus beseitigen, zum Beispiel durch Aufteilen des Zählers. False Sharing bedeutet, dass die Daten logisch unabhängig sind und nur zufällig im Speicher benachbart liegen, sodass die Abhilfe eine Änderung des Datenlayouts ist. Beide erzeugen dasselbe Symptom: starken Kohärenzverkehr auf wenigen Lines. Rein lesendes Teilen verursacht keines der beiden Probleme, weil viele Caches eine Line gleichzeitig im Zustand Shared halten können; nur Schreibvorgänge erzwingen Invalidierungen.

Typische Verursacher

Der klassische Fall ist ein Array von Zählern pro Thread: Bei 8-Byte-Elementen passen acht davon in eine 64-Byte-Line, sodass bis zu acht Threads um sie kämpfen. Weitere häufige Quellen sind Structs, deren Felder von verschiedenen Threads aktualisiert werden, ein Lock in derselben Line wie Daten, die von einem anderen Lock geschützt werden, und Arbeitswarteschlangen, deren Head- und Tail-Indizes, geschrieben von Producer und Consumer, nebeneinanderliegen. Das übliche Anzeichen ist ein Programm, dessen Speedup mit mehr Threads abflacht oder sogar sinkt, obwohl jeder Thread scheinbar nur seine eigenen Daten berührt.

Wie man es behebt und findet

Jedes unabhängig geschriebene Element auf die Größe einer Cache-Line auffüllen (Padding) oder ausrichten, etwa mit alignas(64) in C oder C++, sodass jeder Thread seine eigene Line besitzt. Manche Prozessoren holen benachbarte Line-Paare gemeinsam, weshalb mitunter ein Abstand von 128 Byte verwendet wird. Noch besser ist es, jeden Thread in einer lokalen Variable oder einem Register akkumulieren zu lassen und die gemeinsame Stelle am Ende einmal zu schreiben. Hardware-Performance-Counter können das Problem aufdecken; unter Linux meldet das Werkzeug perf c2c Cache-Lines, die häufig von einem Kern geändert und dann von einem anderen getroffen werden.

Jetzt üben: Fragen zu False Sharing

Antwort und Erläuterung anzeigen

Antwort: A. Obwohl verschiedene Threads verschiedene Variablen ändern, liegen diese in derselben Cache-Zeile, sodass die Zeile zwischen den Kernen hin- und herwandert und es langsam wird

Kohärenz wird in Einheiten der Cache-Zeile (im Allgemeinen 64 Byte) verwaltet. Auch wenn Kern 0 nur Variable a und Kern 1 nur Variable b ändert, werden bei Lage von a und b in derselben Zeile bei jedem Schreiben die Kopien des anderen ungültig, und die Zeile wandert zwischen den beiden Kernen hin und her. Das Ergebnis ist korrekt, die Leistung sinkt aber stark; das ist False Sharing. Das Problem tritt leicht bei Arrays für threadweise Zählungen auf.

In einem Array von Zählern je Thread wie „long cnt[8];“ tritt False Sharing auf. Welche Gegenmaßnahme ist am besten geeignet?

  1. ADen Zählertyp von long auf int ändern und das Array verkleinern
  2. BZwischen den Zählern Füllbytes einfügen oder sie ausrichten, sodass sie in verschiedenen Cache-Zeilen liegen
  3. CDie Zahl der Threads erhöhen, um die Wartezeiten zu verteilen
Antwort und Erläuterung anzeigen

Antwort: B. Zwischen den Zählern Füllbytes einfügen oder sie ausrichten, sodass sie in verschiedenen Cache-Zeilen liegen

Bei 8 Byte großem long passen die 8 Zähler in eine Zeile von 64 Byte, und alle Threads streiten um dieselbe Zeile. Fügt man Füllbytes ein, sodass jeder Zähler auf einer 64-Byte-Grenze liegt, oder richtet man die Struktur an der Größe der Cache-Zeile aus, kann jeder Thread eine eigene Zeile nutzen. Wirksam ist auch, dass jeder Thread in einer lokalen Variablen zählt und erst am Ende einmal auf den gemeinsamen Speicherplatz addiert.

Häufige Fragen

Führt False Sharing zu falschen Ergebnissen?

Nein. Das Kohärenzprotokoll hält jede Variable korrekt; False Sharing kostet nur Zeit, weil die Cache-Line mit den Variablen ständig zwischen den Kernen wandert.

Wie viel Padding braucht man gegen False Sharing?

So viel, dass jede unabhängig geschriebene Variable eine eigene Cache-Line belegt, meist 64 Byte. Mancher Code verwendet 128 Byte, weil bestimmte CPUs benachbarte Line-Paare gemeinsam vorab holen.

Können nur gelesene gemeinsame Daten False Sharing verursachen?

Nein. Mehrere Kerne können dieselbe Line gleichzeitig in einem gemeinsamen Zustand halten; das Problem tritt nur auf, wenn mindestens ein Thread in die Line schreibt.
