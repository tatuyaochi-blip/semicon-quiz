Was ist RPO (Recovery Point Objective)?

Ein Ziel, das angibt, auf welchen Zeitpunkt Daten bei einer Störung oder Katastrophe wiederherstellbar sein müssen. Bei einem RPO von 1 Stunde dürfen höchstens die Daten der letzten Stunde verloren gehen; Backups oder Kopien der Daten müssen also mindestens stündlich erstellt werden.

Japanische Bezeichnung: RPO(目標復旧時点)

„RPO (Recovery Point Objective)“ kommt in 3 Übungsfragen aus 2 Themen vor, z. B. Systemarchitektur und Zuverlässigkeit, IT-Service-Management und IT-Audit.

Fachgebiet: Systemarchitektur und Zuverlässigkeit

RPO und RTO

Das RPO ist ein Ziel dafür, wie weit zurück die Wiederherstellung reichen darf, also die Datenmenge, die verloren gehen darf, ausgedrückt als Zeit. Das RTO (Recovery Time Objective) ist ein Ziel dafür, wie lange die Wiederaufnahme dauern darf. Bei einem RPO von 4 Stunden und einem RTO von 2 Stunden darf eine Störung zum Beispiel keine Daten verlieren, die älter als 4 Stunden sind, und der Geschäftsbetrieb muss innerhalb von 2 Stunden wieder aufgenommen werden. Es sind getrennte Ziele, daher muss ein Verfahren gewählt werden, das beide erfüllt.

Wege, das RPO einzuhalten

Verlässt sich der Schutz allein auf periodische Backups, gehen bei einer Störung kurz vor dem nächsten Backup die Daten des gesamten Backupintervalls verloren. Das Backupintervall wird daher nicht länger als das RPO gewählt. Um das RPO auf Minuten oder nahe null zu senken, werden Änderungsprotokolle der Datenbank häufig an einen anderen Ort gesendet, oder eine Replikation kopiert die Daten auf einen anderen Server.

Synchrone und asynchrone Replikation

Die synchrone Replikation schließt eine Änderung erst ab, nachdem bestätigt ist, dass das Schreiben auch am Replikat abgeschlossen ist; bei einer Störung gehen daher keine Daten verloren (ein RPO von null). Dafür kommt die Laufzeit für den Hin- und Rückweg zum Replikat zu jeder Änderung hinzu, sodass die Antworten zwischen weit entfernten Standorten langsam werden. Die asynchrone Replikation sendet die Kopien später, die Antworten sind also schnell, bei einer Störung können aber noch nicht gesendete Daten verloren gehen.

Das RPO (Recovery Point Objective) ist ein Ziel, das angibt, auf welchen Zeitpunkt die Daten bei einer Störung wiederherstellbar sein müssen. Ein RPO von 1 Stunde bedeutet zum Beispiel, dass die Daten auf einen Zeitpunkt innerhalb der Stunde vor der Störung wiederherstellbar sein müssen; Backups oder Kopien der Daten müssen also mindestens stündlich erstellt werden. Die bis zur Wiederaufnahme des Geschäftsbetriebs zulässige Zeit ist das RTO (Recovery Time Objective), und je kürzer RPO und RTO sind, desto teurer sind die nötigen Einrichtungen.

Für ein System werden ein RPO (Recovery Point Objective) von 4 Stunden und ein RTO (Recovery Time Objective) von 2 Stunden festgelegt. Eine Störung kann jederzeit auftreten, und die Zeit für das Erstellen eines Backups ist vernachlässigbar. Welches Datenschutzverfahren erfüllt diese Ziele?

  2. BBackups werden alle 3 Stunden erstellt, und die Wiederherstellung dauert bei einer Störung 1,5 Stunden
  3. CBackups werden alle 6 Stunden erstellt, und die Wiederherstellung dauert bei einer Störung 1 Stunde
Antwort und Erläuterung anzeigen

Antwort: B. Backups werden alle 3 Stunden erstellt, und die Wiederherstellung dauert bei einer Störung 1,5 Stunden

Tritt eine Störung kurz vor dem nächsten Backup auf, gehen die Daten des gesamten Backupintervalls verloren; um das RPO einzuhalten, darf das Backupintervall daher nicht länger als das RPO sein. Außerdem darf die Wiederherstellung nicht länger als das RTO dauern. Mit Backups alle 3 Stunden und einer Wiederherstellung in 1,5 Stunden gehen höchstens Daten von 3 Stunden verloren (4 Stunden oder weniger), und die Wiederherstellung dauert 1,5 Stunden (2 Stunden oder weniger); beide Ziele sind erfüllt. Das stündliche Verfahren verfehlt das RTO, das Verfahren mit 6 Stunden das RPO.

Häufige Fragen

Sind kürzere RPOs und RTOs immer besser?

Kürzere Werte verringern die Folgen von Störungen, aber die Kosten für Replikation, Standby-Einrichtungen und Betriebsaufwand steigen. Üblich ist, sie für jeden Geschäftsprozess festzulegen, indem die Verluste durch stillstehenden Betrieb oder verlorene Daten mit den Kosten der Maßnahmen verglichen werden.

Lässt sich ein System mit einem RPO von null bauen?

Mit synchroner Replikation ist eine Konfiguration möglich, die bis zum Zeitpunkt der Störung keine Daten verliert. Werden Daten jedoch durch eine Fehlbedienung oder einen Softwarefehler beschädigt, wird auch der beschädigte Zustand repliziert; Backups, mit denen sich frühere Zeitpunkte wiederherstellen lassen, sind daher weiterhin zusätzlich nötig.
