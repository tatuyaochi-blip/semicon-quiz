Was ist Shared Library (gemeinsam genutzte Bibliothek)?

Bibliothek, die beim dynamischen Linken zur Laufzeit geladen wird. Unter Linux .so, unter Windows .dll. Sie wird als positionsunabhängiger Code erstellt, und die Codeseiten können von vielen Prozessen gemeinsam genutzt werden.

Japanische Bezeichnung: 共有ライブラリ

Fachgebiet: Linker, Loader und ausführbare Formate

Wie dynamisches Linken funktioniert

Wird ein Programm gegen eine Shared Library gelinkt, hält die ausführbare Datei nur fest, welche Bibliotheken sie benötigt, identifiziert über ihren Soname, und welche Symbole sie importiert. Beim Start findet der dynamische Linker (ld.so unter Linux) jede Bibliothek, bildet sie in den Adressraum des Prozesses ab, löst Symbolverweise auf und wendet Relokationen an. Aufrufe von Bibliotheksfunktionen laufen typischerweise über die Procedure Linkage Table (PLT), die jede Funktion verzögert (lazy) bei ihrem ersten Aufruf auflösen kann. Der Befehl ldd zeigt, zu welcher Datei jede benötigte Bibliothek aufgelöst wird, und kennzeichnet fehlende als „not found“; er sollte nicht auf nicht vertrauenswürdige Binärdateien angewendet werden, da dies deren Code ausführen kann.

Positionsunabhängiger Code und gemeinsam genutzte Seiten

Eine Shared Library kann in jedem Prozess an einer anderen Adresse landen, daher wird sie als positionsunabhängiger Code (PIC) kompiliert. Der Code erreicht seine eigenen Funktionen und Daten mit PC-relativer Adressierung und externe Symbole über die Global Offset Table (GOT), einen prozesseigenen Datenbereich, den der dynamische Linker füllt. Die Codeseiten müssen daher nie gepatcht werden und können schreibgeschützt und ausführbar abgebildet werden. Das Betriebssystem lässt die Abbildung jedes Prozesses auf dieselben physischen Seiten zeigen, sodass 100 Prozesse, die eine Bibliothek verwenden, deren Code nur einmal im Speicher halten, während beschreibbare Datenseiten pro Prozess geführt werden, typischerweise mit Copy-on-Write.

Versionierung mit Sonames

Unter Linux trägt eine Bibliotheksdatei wie libfoo.so.1.2.3 einen Soname wie libfoo.so.1, und Programme speichern den Soname. Eine Fehlerbehebung oder ein Sicherheitspatch, der die ABI (Application Binary Interface) kompatibel hält, behält den Soname bei, sodass das Ersetzen einer einzigen Datei jedes Programm aktualisiert, das sie verwendet. Geänderte Argumenttypen, geänderte Struct-Layouts oder entfernte Funktionen machen alte Binärdateien funktionsunfähig; daher wird die Soname-Nummer erhöht und die neue Bibliothek neben der alten installiert.

Shared Library und statische Bibliothek im Vergleich

Eine statische Bibliothek ist ein Archiv aus Objektdateien, deren benötigte Teile beim Linken in die ausführbare Datei kopiert werden; das ergibt eine eigenständige Binärdatei ohne Bindung beim Start, doch jedes Programm trägt seine eigene Kopie, und eine Fehlerbehebung erfordert erneutes Linken. Shared Libraries sparen Arbeitsspeicher und Plattenplatz und erlauben Aktualisierungen an Ort und Stelle, um den Preis von Bindungsarbeit beim Start, einer Indirektion bei modulübergreifenden Aufrufen und Fehlern durch fehlende Abhängigkeiten. Internen Funktionen verborgene Sichtbarkeit (Hidden Visibility) zu geben und nur die öffentliche API zu exportieren, verringert die Zahl der Symbole, die der dynamische Linker verarbeiten muss, lässt interne Aufrufe die PLT umgehen, vermeidet Namenskonflikte und hält die ABI klein.

Wie wird der physische Speicher genutzt, wenn 100 Prozesse dieselbe Shared Library verwenden?

  2. BSowohl Code als auch Daten liegen pro Prozess in 100 Kopien vor
  3. CAlles einschließlich der Datenseiten wird gemeinsam genutzt, sodass die Prozesse gegenseitig ihre Werte sehen
Antwort und Erläuterung anzeigen

Antwort: A. Seiten mit unveränderlichem Code teilen sich eine Kopie, Seiten mit beschreibbaren Daten hat jeder Prozess für sich

Das Betriebssystem bildet die Shared Library in den virtuellen Adressraum jedes Prozesses ab, und Seiten mit unveränderlichem Code und Konstanten verweisen auf dieselben physischen Seiten. Seiten mit beschreibbaren Daten wie Variablen werden pro Prozess getrennt gehalten, indem z. B. beim ersten Schreiben eine Kopie angelegt wird (Copy-on-Write). So genügt für den Code der Bibliothek auch bei 100 Prozessen ein einziger Speicherbereich.

Welcher Vorteil ergibt sich, wenn man beim Erstellen einer Shared Library nur die von außen genutzten Funktionen veröffentlicht und die Sichtbarkeit (Visibility) der Symbole interner Funktionen auf „hidden“ setzt?

  1. ADie internen Funktionen werden verschlüsselt und sind nicht analysierbar
  2. BDie Zahl der vom dynamischen Linker behandelten Symbole sinkt, das Laden wird schneller, und interne Aufrufe müssen nicht über die PLT laufen
  3. CDie Bibliothek läuft auf jedem Betriebssystem
Antwort und Erläuterung anzeigen

Antwort: B. Die Zahl der vom dynamischen Linker behandelten Symbole sinkt, das Laden wird schneller, und interne Aufrufe müssen nicht über die PLT laufen

Veröffentlichte Symbole einer Shared Library können durch gleichnamige Definitionen anderer Module ersetzt werden; auch interne Aufrufe müssen daher über PLT und GOT laufen. Mit hidden sind sie von außen nicht sichtbar, die Zahl der vom dynamischen Linker zu prüfenden Symbole sinkt, und interne Aufrufe können direkt PC-relativ erfolgen. Auch Namenskollisionen mit anderen Bibliotheken werden vermieden, und die veröffentlichte ABI bleibt klein.

Häufige Fragen

Unterschied zwischen statischer Bibliothek und Shared Library

Eine statische Bibliothek (.a oder .lib) wird beim Linken in die ausführbare Datei kopiert. Eine Shared Library (.so oder .dll) bleibt eine separate Datei, die zur Laufzeit geladen wird und im Speicher von vielen Prozessen gemeinsam genutzt werden kann.

Warum brauchen Shared Libraries -fPIC?

Die Bibliothek kann an jeder beliebigen Adresse geladen werden, daher muss ihr Code absolute Adressen vermeiden. PIC nutzt PC-relative Adressierung und die GOT, sodass die Codeseiten nicht verändert werden müssen und gemeinsam genutzt werden können.

Was bedeutet „not found“ in der Ausgabe von ldd?

Der dynamische Linker kann diese Shared Library in seinem Suchpfad nicht finden; das Programm startet daher nicht, bis die Bibliothek installiert oder der Pfad korrigiert ist.
