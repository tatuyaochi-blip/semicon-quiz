Was ist Data Race (Datenwettlauf)?

Zustand, in dem mehrere Threads ohne Synchronisation gleichzeitig auf dieselbe Variable zugreifen und mindestens einer schreibt. Das Ergebnis variiert von Lauf zu Lauf. In C und C++ undefiniertes Verhalten.

Japanische Bezeichnung: データ競合

„Data Race (Datenwettlauf)“ kommt in 5 Übungsfragen aus 2 Themen vor, z. B. Multicore und Synchronisation, Embedded Systems und Firmware.

Fachgebiet: Multicore und Synchronisation

Wie ein Update verloren geht

Die Anweisung counter++ wirkt atomar, wird aber in drei Schritte übersetzt: Wert laden, 1 addieren, zurückspeichern. Angenommen, zwei Threads erhöhen einen gemeinsamen Zähler jeweils 100.000-mal. Lädt Thread A den Wert 100 und Thread B ebenfalls 100, bevor A speichert, speichern beide 101, und eine Erhöhung geht verloren. Je nachdem, wie sich die Threads verzahnen, kann der Endwert irgendwo unter 200.000 liegen und von Lauf zu Lauf variieren. Nichts stürzt ab, daher wird der Fehler leicht übersehen, und er kann verschwinden, wenn das Programm durch einen Debugger oder Logging verlangsamt wird.

Data Race vs. Race Condition

Ein Data Race ist präzise definiert: Zwei Threads greifen gleichzeitig auf dieselbe Speicherstelle zu, mindestens ein Zugriff ist ein Schreibzugriff, und keine Synchronisation legt ihre Reihenfolge fest. Eine Race Condition ist weiter gefasst: jeder Fehler, dessen Ergebnis vom Timing abhängt. Beide überschneiden sich, sind aber nicht identisch. Eine Prüfen-dann-Handeln-Sequenz aus einzeln atomaren Operationen enthält keinen Data Race, kann aber dennoch eine Race Condition sein, weil ein anderer Thread zwischen Prüfen und Handeln eingreifen kann. Sprachen behandeln Data Races unterschiedlich: In C und C++ hat ein Programm mit einem Data Race undefiniertes Verhalten, während Java solchen Programmen eine definierte, aber schwache Semantik gibt.

Abhilfe: Locks und atomare Operationen

Die Abhilfe besteht darin, den konkurrierenden Zugriffen eine Reihenfolge aufzuzwingen. Ein Lock (Mutex) macht das Update zu einem kritischen Abschnitt, den jeweils nur ein Thread ausführt; kurze kritische Abschnitte begrenzen die Wartezeit. Für einfache Operationen sind atomare Befehle schneller: Fetch-and-Add, etwa lock xadd auf x86 oder amoadd.w auf RISC-V, führt Lesen, Addieren und Schreiben unteilbar aus und gibt den alten Wert zurück, muss also nie wiederholt werden. Komplexere Updates nutzen Compare-and-Swap-Schleifen. Eine Variable in C oder C++ als volatile zu deklarieren, verhindert keinen Data Race, da es weder Atomarität noch eine Reihenfolge zwischen Threads liefert.

Warum Compiler und Hardware Races verschärfen

Da C und C++ Programme ohne Data Races voraussetzen, dürfen Compiler eine gemeinsame Variable in einem Register halten, einen Ladebefehl aus einer Schleife herausziehen oder Speicherbefehle zusammenfassen; ein Thread, der auf ein von einem anderen Thread ohne Synchronisation geschriebenes Flag wartet, sieht die Änderung dann womöglich nie. Die Hardware fügt durch Store-Buffer und Caches eigene Umordnungen hinzu. Erst Synchronisationsoperationen wie das Erwerben eines Locks und atomare Operationen mit passender Speicherordnung zeigen Compiler und Hardware an, wo die Reihenfolge erhalten bleiben muss. Dynamische Race-Detektoren wie ThreadSanitizer helfen, Races zu finden, die durch Tests allein selten zutage treten.

Antwort: C. Mehrere Threads greifen ohne Synchronisation gleichzeitig auf dieselbe Variable zu, und mindestens einer davon schreibt

Ein Data Race ist ein Zustand, in dem die Reihenfolge von Lese- und Schreibzugriffen auf dieselbe Stelle nicht durch Synchronisation festgelegt ist und das Ergebnis davon abhängt, in welcher Reihenfolge ausgeführt wurde. Da er je nach Timing auftritt oder nicht, ist er ein schwer durch Tests zu findender Fehler. In C und C++ ist das Verhalten von Programmen mit Data Race undefiniert. Die Reihenfolge muss durch Sperren oder atomare Variablen festgelegt werden.

Häufige Fragen

Was ist der Unterschied zwischen Data Race und Race Condition?

Ein Data Race ist ein gleichzeitiger, nicht synchronisierter Zugriff auf dieselbe Speicherstelle, bei dem mindestens ein Zugriff schreibt. Eine Race Condition ist jeder timingabhängige Fehler und kann auch dann bestehen, wenn jeder einzelne Zugriff korrekt synchronisiert ist.

Kann ein Data Race auf einer Single-Core-CPU auftreten?

Ja. Unterbricht das Betriebssystem einen Thread zwischen Laden und Speichern, kann ein anderer Thread laufen und dieselbe Variable ändern, sodass eine Erhöhung auch ohne echte Parallelität verloren gehen kann.

Verhindert das Schlüsselwort volatile Data Races in C und C++?

Nein. volatile zwingt den Compiler nur, jeden Zugriff tatsächlich auszuführen; es macht Read-Modify-Write-Sequenzen weder atomar, noch ordnet es sie zwischen Threads. Stattdessen sollten atomare Operationen oder Locks verwendet werden.
