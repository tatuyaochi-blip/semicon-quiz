What is Static library?

An archive bundling many object files (.a on Linux). During static linking, the linker extracts only the objects it needs into the executable.

Japanese name: 静的ライブラリ

What is inside a .a file

On Unix-like systems a static library is an archive created with the ar tool, for example ar rcs libfoo.a a.o b.o. It is little more than the object files concatenated with headers, plus an index mapping each defined global symbol to the member that defines it, so the linker can find definitions without scanning every member. The command-line option -lfoo makes the linker look for libfoo.so or libfoo.a in the library search path; GNU ld prefers the shared version when both exist unless static linking is requested. Windows toolchains use .lib files for the same purpose.

The unit of extraction is the object file

When a member is needed, the linker includes the whole object file, not just the one function that was referenced. If a library's source file defines twenty functions and a program calls one, all twenty land in the executable, along with anything they reference in turn. Libraries such as the C standard library are therefore often built from many small source files, sometimes one function each. Alternatively, compiling with -ffunction-sections and -fdata-sections and linking with --gc-sections lets the linker drop unreferenced functions within a member.

Link order and circular dependencies

The GNU linker scans inputs left to right and, on reaching an archive, extracts only members that resolve references undefined at that moment, then never revisits it. Libraries must therefore come after the objects that use them, and a library that depends on another must come before it. When two libraries depend on each other, the usual fixes are listing one twice or wrapping both in --start-group and --end-group so the linker rescans them until nothing new is resolved. Some linkers, such as LLVM's lld, remember all archive symbols and do not need this ordering.

Static library vs. shared library

A static library is consumed only at build time: its code is copied into each executable, and the .a file is not needed when the program runs. A shared library (.so on Linux, .dll on Windows) is a single linked file, built as position-independent code, that is loaded at run time and whose pages are shared among all processes using it. Static libraries suit self-contained deployment and embedded firmware, while shared libraries save disk and memory and let a fix reach every program by replacing one file.

Answer: C. Only the object files in the library that are needed to resolve undefined references

A static library is an archive bundling many object files. The linker extracts and includes only those object files that define symbols still lacking a definition. So even with a library containing many functions, such as the standard library, the executable grows only by the functions actually used.

Answer: A. The linker works left to right and does not extract functions not yet referenced when it reads the library

The GNU linker processes files in command-line order, and when it meets a static library it extracts only the objects that resolve references still undefined at that moment. If the library comes first, main.o's references do not exist yet, so nothing is extracted, and the linker does not go back after reading main.o. That is why libraries are normally written after the files that use them.

FAQ

How do I create a static library in Linux?

Compile the sources to object files with gcc -c, then bundle them with ar rcs libname.a file1.o file2.o. Link against it with -L pointing to its directory and -lname.

What is the difference between a .a and a .so file?

A .a file is an archive of object files whose needed members are copied into the executable at link time. A .so file is a shared library loaded at run time and shared among processes.

Why do I get undefined reference errors even though I linked the library?

With the GNU linker the most common cause is order: the library appears on the command line before the object files that use it. Move -lname after the objects, and check the library actually defines the symbol with nm.
