What is JIT compilation?

Compiling frequently executed parts of a program to machine code while it runs, enabling optimizations based on run-time information. Used in runtimes for Java, JavaScript and others.

Field: Compilers

Tiered execution

A typical JIT (just-in-time) runtime starts by interpreting bytecode, which costs nothing up front but runs slowly. While interpreting, it counts how often each method is called and each loop iterates. Code that crosses a threshold is handed to a quick baseline compiler, and code that stays hot is later recompiled by an optimizing compiler that spends much more time per function. Long-running loops can be switched to compiled code in the middle of execution, a technique called on-stack replacement. Compilation usually happens on background threads so the program keeps running meanwhile.

Speculation and deoptimization

The interpreter and baseline code collect profiles: which branches are taken, which object types appear at each call site, whether integers have ever overflowed. The optimizing compiler bets on these observations, for example inlining the one method a virtual call has always reached and dropping code for types never seen. Each bet is protected by a cheap guard. If a guard fails, the runtime deoptimizes: it rebuilds the interpreter's view of the current frame, continues in slower code and may later recompile with the new information. Ahead-of-time compilers cannot make such bets so freely.

JIT vs. AOT vs. interpreter

A pure interpreter starts instantly and needs no compiler at run time, but executes each operation slowly. AOT (ahead-of-time) compilation produces machine code before the program runs, giving fast start-up, predictable performance and no compiler in memory, but it must optimize without knowing actual inputs, unless profile-guided optimization supplies training-run data. A JIT pays for warm-up time, compilation CPU time and memory for the code cache, and in return can reach high peak speed on long-running programs. Many runtimes combine approaches, for example caching or AOT-compiling start-up code.

Practical constraints

A JIT writes machine code into memory and then executes it, which conflicts with the security rule that memory should not be writable and executable at the same time. Runtimes handle this by switching page permissions after emitting code, or by mapping the same physical memory twice with different permissions, and some locked-down platforms forbid run-time code generation entirely. Because compiled code depends on run-time profiles, performance can vary between runs and can drop suddenly when deoptimization occurs, which makes benchmarking JIT-based systems require proper warm-up.

  3. CBytecode is interpreted one instruction at a time forever, never using machine code
Show answer and explanation

Answer: B. Hot code is compiled during execution, using run-time information

With JIT compilation, bytecode is first interpreted, and when frequently executed parts (hot spots) are found, they are compiled to machine code while the program runs. Run-time information, such as which branches are taken and which types are passed, enables aggressive optimizations hard to achieve ahead of time, with a fallback to interpretation if assumptions fail. Translating everything beforehand is ahead-of-time (AOT) compilation, and only interpreting is a pure interpreter.

FAQ

Is JIT compilation faster than AOT compilation?

It depends on the workload. JIT code can match or beat AOT code on long-running programs because it optimizes using real profiles, but AOT wins on start-up time, memory use and predictability.

What is JIT warm-up?

The initial period in which code runs in the interpreter or a baseline tier while the runtime profiles it and compiles hot parts. Performance measured during warm-up underestimates steady-state speed.

What is deoptimization in a JIT?

Abandoning optimized code when an assumption it was built on turns out false, and continuing execution in the interpreter or less-optimized code from the equivalent point. The runtime may then recompile with updated profile information.
