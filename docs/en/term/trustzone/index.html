What is TrustZone?

Arm's processor security architecture, switching between secure and normal worlds and using bus signals to distinguish and restrict access to memory and peripherals.

Japanese name: TrustZone

TrustZone appears in 3 practice questions across 2 topics, including Hardware Security, Hardware Security: Advanced Topics and Trends.

Field: Hardware Security

Two worlds on one processor

TrustZone gives an Arm core two security states: the secure world and the normal world. The rich operating system and ordinary applications run in the normal world, while a small trusted OS and its trusted applications run in the secure world. On Cortex-A processors, switching between them passes through a secure monitor entered with the SMC (secure monitor call) instruction, which saves one world's context and restores the other's. The same core, caches and memory system are time-shared between the two, so a secure area is created inside a single system on chip (SoC) without adding a separate security processor.

How the bus enforces isolation

Security state is not just a software convention. Every transaction the core places on the on-chip bus carries a signal marking whether it is secure or non-secure. Address space controllers in front of DRAM, on-chip SRAM and peripherals check that signal and reject non-secure accesses to regions assigned to the secure world. Peripherals such as a fingerprint sensor interface or a crypto engine can likewise be reserved for secure software, and caches tag lines by world. As a result, even a fully compromised normal-world kernel cannot read secure memory, because the hardware blocks the access itself.

TrustZone as a trusted execution environment

A trusted execution environment (TEE) is a small, hardware-isolated environment for work that must survive a compromise of the main OS. TrustZone is the most widely used basis for a TEE on smartphones and similar devices. Typical secure-world tasks are biometric matching, payment credential handling, storage of digital rights management (DRM) keys and verification steps during secure boot. Keeping the trusted code base small is the point: a large OS cannot be made free of vulnerabilities, but a compact trusted OS with a narrow interface is much easier to review and harden.

TrustZone vs. a separate secure element

TrustZone isolates software logically but shares physical resources such as cores, caches and power rails with the normal world. That keeps cost low but leaves exposure to side-channel and fault-injection attacks that a dedicated chip can resist better. A secure element is a separate, tamper-resistant chip with its own processor and memory, often used alongside a TEE for the most valuable keys. Microcontroller-class Armv8-M cores implement a lighter TrustZone variant in which secure and non-secure code call each other directly through defined entry points, without a monitor.

Answer: C. The CPU has secure-world and normal-world states, and bus signals distinguish which world each memory or peripheral access comes from, enforcing restrictions

In TrustZone, a CPU core switches between secure and normal states, and every access carries a bus signal indicating which state issued it. Logic on the memory and peripheral side checks this signal and rejects normal-world accesses to regions assigned to the secure world. It creates a secure area within a single SoC without an extra chip, so it is widely used in smartphones and similar devices.

FAQ

What is Arm TrustZone used for?

It is used to run security-critical code such as biometric matching, payment processing, key storage and secure boot checks in a hardware-isolated secure world. Even if the normal operating system is compromised, the secure world's memory and keys remain inaccessible.

What is the difference between TrustZone and a TEE?

A TEE is the general concept of an isolated execution environment protected by hardware. TrustZone is Arm's hardware mechanism that provides the isolation on which a TEE's trusted OS and applications are built.

How does TrustZone stop the normal world from reading secure memory?

Each bus transaction carries a signal indicating whether it came from the secure or normal state. Controllers in front of memory and peripherals check that signal and refuse normal-world accesses to secure regions.
