What is Handshake?

A scheme that transfers data reliably by exchanging a request (req) from the sender and an acknowledgment (ack) from the receiver. Across clock domains only req and ack are synchronized while the data is held stable, which is safe but takes several cycles or more per transfer.

Japanese name: ハンドシェイク

The four-phase sequence

In a four-phase (return-to-zero) handshake the sender first places data on the bus and holds it, then raises req. The receiver sees the synchronized req, captures the data and raises ack. The sender sees the synchronized ack and lowers req, and the receiver, seeing req fall, lowers ack. Each signal rises and falls once, four transitions per transfer. The critical rule is ordering: data must be stable before req rises and must not change until ack confirms capture, or the receiver may catch a value in transition.

Why it is safe across clock domains

Only req and ack cross between domains, and each is a single bit passed through an ordinary two-flop synchronizer. The multi-bit data is never synchronized; by the time the receiver sees req, the data has been stable for several cycles and can be captured directly. This removes the bit-skew problem that breaks per-bit synchronization of a bus, works for any frequency ratio, and never loses an event because the sender waits for confirmation. That waiting is what distinguishes it from toggle synchronization, which requires a guaranteed minimum spacing between events.

The price is latency

Every transition must pass through a synchronizer, typically two cycles each way, and four-phase signaling needs two round trips, so one transfer costs eight or more cycles in total across both domains. A two-phase variant treats each toggle of req or ack as an event, halving the transitions at the cost of edge-detection logic. Either way, throughput is far below one word per cycle, so handshakes suit occasional transfers such as control-register writes, while streaming data goes through an asynchronous FIFO.

Handshakes within one clock: VALID/READY

The same request–acknowledge idea appears in synchronous buses, without synchronizers. In AXI, every channel uses VALID from the sender and READY from the receiver, and a transfer occurs on any clock edge where both are 1. Holding READY low applies backpressure, so blocks of different speeds connect without losing data. To avoid deadlock, the sender must not wait for READY before asserting VALID. AXI has five independent channels for read address, read data, write address, write data and write response; AXI4-Stream drops addresses for one-way data flow.

In a four-phase handshake, req takes two synchronization cycles to reach the receiver and ack two cycles to return to the sender, and returning each to 0 takes the same again, so one transfer takes 8 or more cycles in total across both domains. It therefore suits data passed occasionally, such as control register settings. The data stays stable throughout the transfer, so errors from bit misalignment do not occur, and any frequency ratio works. For streaming data almost every cycle, use an asynchronous FIFO.

FAQ

What is the difference between two-phase and four-phase handshakes?

In four-phase signaling req and ack each rise and then return to zero, so one transfer uses four transitions. In two-phase signaling every toggle is an event, so a transfer needs only two transitions, roughly halving latency but requiring edge detection.

Does an AXI VALID/READY handshake need synchronizers?

No, VALID/READY operates within a single clock domain and transfers on any edge where both are high. When AXI traffic must cross clock domains, an asynchronous bridge, usually built from asynchronous FIFOs, is inserted.

Why is a req/ack handshake slow for clock domain crossing?

Each req and ack transition passes through a multi-cycle synchronizer and the sender must wait for the reply, so a full transfer takes eight or more cycles. That is acceptable for occasional data but not for continuous streams.
