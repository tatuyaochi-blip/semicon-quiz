What is Shared library?

A library loaded at run time by dynamic linking: .so on Linux, .dll on Windows. Built as position-independent code, its code pages can be shared by many processes.

Japanese name: 共有ライブラリ

How dynamic linking works

When a program is linked against a shared library, the executable records only which libraries it needs, identified by their soname, and which symbols it imports. At start-up the dynamic linker (ld.so on Linux) finds each library, maps it into the process's address space, resolves symbol references and applies relocations. Calls to library functions typically go through the procedure linkage table (PLT), which can resolve each function lazily on its first call. The ldd command shows which file each needed library resolves to and flags missing ones as "not found"; it should not be run on untrusted binaries, since that can execute their code.

Position-independent code and page sharing

A shared library may land at a different address in every process, so it is compiled as position-independent code (PIC). Code reaches its own functions and data with PC-relative addressing and reaches external symbols through the global offset table (GOT), a per-process data area that the dynamic linker fills in. The code pages therefore never need patching and can be mapped read-only and executable. The OS points every process's mapping at the same physical pages, so 100 processes using one library hold its code once, while writable data pages are kept per process, typically with copy-on-write.

Versioning with sonames

On Linux a library file such as libfoo.so.1.2.3 carries a soname such as libfoo.so.1, and programs record the soname. A bug fix or security patch that keeps the ABI (application binary interface) compatible keeps the soname, so replacing one file updates every program that uses it. Changing argument types, struct layouts or removing functions breaks old binaries, so the soname number is raised and the new library is installed alongside the old one.

Shared vs. static libraries

A static library is an archive of object files whose needed parts are copied into the executable at link time, giving a self-contained binary with no start-up binding, but every program carries its own copy and a fix requires relinking. Shared libraries save memory and disk and allow in-place updates, at the price of start-up binding work, an indirection on cross-module calls, and missing-dependency failures. Giving internal functions hidden visibility and exporting only the public API reduces the symbols the dynamic linker must process, lets internal calls skip the PLT, avoids name clashes and keeps the ABI small.

Answer: A. The read-only code pages are shared as one copy, while writable data pages are held per process

The OS maps the shared library into each process's virtual address space so that pages of unchanging code and constants point to the same physical pages. Pages of writable data such as variables are kept separate per process, for example by copying a page when it is first written (copy-on-write). So even with 100 processes, the library's code occupies memory only once.

Answer: C. When a change breaks ABI compatibility with old programs, such as altering function arguments or struct layouts

A dynamically linked program uses, at run time, the shared library named by its soname. A compatible fix keeps the same soname, so replacing the file updates every program. Changing argument types or struct sizes, however, would make old programs call with wrong assumptions, so the soname number is raised to treat it as a different library that can be installed alongside the old one.

FAQ

What is the difference between a static library and a shared library?

A static library (.a or .lib) is copied into the executable at link time. A shared library (.so or .dll) stays a separate file loaded at run time and can be shared in memory by many processes.

Why do shared libraries need -fPIC?

The library can be loaded at any address, so its code must avoid absolute addresses. PIC uses PC-relative addressing and the GOT so code pages need no modification and can be shared.

What does "not found" in ldd output mean?

The dynamic linker cannot locate that shared library in its search path, so the program will fail to start until the library is installed or the path is fixed.
