What is Dynamic linker?

Software that, when a dynamically linked program starts, finds and loads shared libraries, applies relocations and binds symbols before starting the program, such as ld.so on Linux.

Japanese name: 動的リンカ

What happens at program start

A dynamically linked ELF executable names an interpreter in its program headers, such as ld-linux on Linux. After execve maps the program, the kernel also maps that dynamic linker and transfers control to it rather than to the program. The dynamic linker reads the list of needed libraries, searches for them in configured paths and its cache, maps them into the address space, applies relocations, binds symbols, runs the libraries' initialization functions (listed in sections such as .init_array), and finally jumps to the program's entry point. Libraries opened later with dlopen go through the same machinery.

GOT, PLT and lazy binding

Shared libraries are built as position-independent code, so their code pages contain no absolute addresses of other modules. Instead, code reads addresses from the global offset table (GOT), a writable data table the dynamic linker fills in. Function calls go through procedure linkage table (PLT) stubs. With lazy binding, the first call through a stub enters the linker's resolver, which writes the real address into the GOT, and later calls jump straight there. Many systems instead bind everything at start-up and then make the GOT read-only (full RELRO) to block GOT-overwrite attacks.

Dynamic linker vs. static linker

The static linker (ld) runs at build time: it combines object files, resolves symbols and applies most relocations, producing an executable. The dynamic linker runs every time the program starts and finishes the job for shared libraries. That split is what lets one physical copy of a library's code be shared by many processes and lets a security fix reach every program by replacing one file. The price is extra start-up work and a dependency on the right library versions being present on the target machine.

Controlling and debugging it

Most start-up failures of dynamically linked programs are missing or incompatible libraries; the ldd command lists the dependencies and shows which ones cannot be found. On Linux, environment variables such as LD_LIBRARY_PATH add search directories and LD_PRELOAD injects a library ahead of others, which is useful for debugging and instrumentation. Library authors can speed up loading by exporting only public functions and marking internal symbols hidden, which reduces the symbols the dynamic linker must process and lets internal calls skip the PLT.

Answer: B. Finding and loading the required shared libraries, binding symbols, then starting the program

A dynamically linked executable names the dynamic linker it uses, and after loading the program the OS first hands control to that dynamic linker. The dynamic linker finds and loads the required shared libraries, applies relocations and binds symbols, then transfers control to the program's entry point. Loading extra libraries at run time with dlopen is also handled by the dynamic linker.

FAQ

What is ld.so on Linux?

It is the dynamic linker/loader: the program the kernel runs first for a dynamically linked executable, which loads shared libraries, resolves symbols and then starts the program.

Why does my program say a shared library cannot be found?

The dynamic linker could not locate a required library, or found only an incompatible version, in its search paths. Running ldd on the program shows which dependency is missing.

What is the difference between the GOT and the PLT?

The GOT is a data table of resolved addresses filled by the dynamic linker, while the PLT is a set of small code stubs that external function calls jump through, reading their targets from the GOT.
