What is Copy-on-write?

Sharing duplicated memory with the original at first and copying a page only when either side tries to write it. It speeds process creation and saves memory.

Japanese name: コピーオンライト

Copy-on-write appears in 5 practice questions across 2 topics, including OS & Hardware, Linkers, Loaders & Executables.

Field: OS & Hardware

How copy-on-write works

When a process is duplicated, the kernel copies only the page tables. Parent and child entries point to the same physical frames, and every writable private page is temporarily marked read-only while the kernel keeps a reference count per frame. Reads proceed at full speed. The first write by either process causes a protection fault; the kernel recognizes a copy-on-write page, allocates a new frame, copies the page, maps the copy as writable for the writer and restarts the faulting instruction. If the reference count shows the page is no longer shared, it can simply be made writable again without copying.

Why it pays off for process creation

A common pattern on Unix-like systems is fork followed almost immediately by exec, for example when a shell starts a command. Exec throws away the entire address space and loads a new program, so eagerly copying the parent's memory would be pure waste. With copy-on-write, fork costs roughly the time to duplicate page tables, and only pages that are actually modified before exec, typically a few stack and data pages, are ever copied. Memory is saved too, because pages that neither side writes, such as code and read-only data, remain shared for the lifetime of both processes.

Where else you will meet it

The same idea appears whenever data is logically duplicated but usually left unmodified. Private file mappings use it: a shared library's writable data section starts out shared with the file cache and each process gets its own copy of a page only when it writes. Many kernels map freshly allocated anonymous memory to a single shared zero page until it is written. Copy-on-write file systems and storage snapshots write modified blocks to new locations instead of overwriting, and virtual machine snapshots and some language runtimes apply the principle to disk images and strings.

Costs and pitfalls

Copy-on-write moves cost rather than eliminating it. Each first write to a shared page takes a fault, a trap into the kernel and a page copy, which is far slower than an ordinary store. If a large process forks and the parent keeps writing to most of its memory, nearly every page is eventually copied and memory use can approach double. Marking pages read-only at fork also requires invalidating stale TLB entries on other cores. Copy-on-write must not be confused with shared memory: with shared memory both processes see each other's writes, while copy-on-write gives each writer a private copy.

Answer: B. Only pages that get written are copied later, so it is fast and saves memory

Copying all memory immediately when duplicating a process is slow and memory-hungry, and wasted if a new program is loaded right after. With copy-on-write, both page tables point to the same physical pages marked read-only; when either side writes, a page fault occurs and the OS copies just that page. Written data is not shared but kept separately in each process, and pages are not all copied.

FAQ

Does fork copy all of the parent's memory?

Not on modern systems. Fork duplicates the page tables and shares physical pages marked read-only; a page is copied only when one of the processes first writes to it.

What happens when a child process writes to memory after fork?

The write triggers a page fault, the kernel copies that single page into a new frame and maps it writable for the child. The parent keeps the original, so neither process sees the other's change.

Is copy-on-write the same as shared memory?

No. Shared memory is deliberately visible to both processes after writes, whereas copy-on-write only shares pages until someone writes, at which point the writer gets a private copy.
