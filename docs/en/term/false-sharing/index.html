What is False sharing?

A slowdown in which threads update different variables that happen to share a cache line, so the line bounces between cores.

Japanese name: 偽共有

Which describes false sharing in a multithreaded program?

  1. AThreads update different variables that sit in the same cache line, so the line bounces between cores and slows things down
  2. BTwo threads update the same variable without synchronization and corrupt it
  3. CThreads wait on each other's locks and stop
Show answer and explanation

Answer: A. Threads update different variables that sit in the same cache line, so the line bounces between cores and slows things down

Coherence is managed per cache line, typically 64 bytes. Even if core 0 writes only a and core 1 writes only b, when a and b share a line each write invalidates the other's copy and the line bounces between the cores. The results are correct but performance drops sharply: this is false sharing. It often occurs with arrays of per-thread counters.

False sharing occurs with an array of per-thread counters such as "long cnt[8];". What is the most suitable fix?

  1. AChange the counters from long to int to shrink the array
  2. BAdd padding or alignment so that each counter sits in its own cache line
  3. CIncrease the number of threads to spread out the waiting
Show answer and explanation

Answer: B. Add padding or alignment so that each counter sits in its own cache line

With 8-byte longs, eight counters fit in a single 64-byte line, and all threads fight over it. Padding so each counter sits 64 bytes apart, or aligning a struct to the cache-line size, gives each thread its own line. Another effective approach is for each thread to count in a local variable and add to the shared location only once at the end.
