What is Speculative execution?

A CPU technique that executes instructions ahead based on predictions, such as branch outcomes, before they are known. Wrong results are discarded, but traces such as cache state may remain.

Japanese name: 投機的実行

Field: Hardware Security

Why CPUs execute ahead of time

A high-performance CPU has a deep pipeline and executes instructions out of order, so waiting for every branch to resolve would leave it idle for many cycles. Instead, a branch predictor guesses the outcome and the core keeps fetching and executing along the predicted path. These speculative results are held in internal buffers and committed, or retired, only once the guess is confirmed. If the prediction was wrong, the core discards the speculative work and restarts on the correct path, so the program's visible results are always correct.

Architectural vs. microarchitectural state

Rolling back a misprediction restores the architectural state, meaning the registers and memory a program can observe directly. It does not undo changes to microarchitectural state such as which lines are in the cache, TLB contents or predictor history. Those changes are normally harmless because programs cannot read them directly, but timing can reveal them: an access to a cached line is measurably faster than one to main memory. This gap between what is rolled back and what is not is the root of speculative-execution vulnerabilities.

How Spectre and Meltdown exploit it

In Spectre, disclosed in 2018 along with Meltdown, an attacker trains the branch predictor so that a path which should never run, such as code past a bounds check, executes speculatively, reads a secret, and uses its value to touch a particular cache line. The results are discarded, but timing which line is cached reveals the secret through a cache side channel. Meltdown abused CPUs that let a speculative load return data from kernel memory before the permission check took effect. Nearly all high-performance CPUs were affected by at least one variant.

Countermeasures and their cost

Mitigations span every layer: operating systems separated kernel and user page tables, compilers insert speculation barriers or use indirect-branch sequences that avoid poisoned predictions, microcode updates add controls over predictor behavior, and newer CPUs build in hardware fixes. Each restriction on speculation, prediction or shared caches reduces leakage but can cost performance, so designers choose how far to go based on what data is at stake. In Spectre, an attacker trains the predictor to mispredict, so a path that should never execute reads secret data and loads a cache location that depends on its value. The results are discarded but the cache state is not restored, so the value can be inferred through a cache side channel.

FAQ

Is speculative execution the same as out-of-order execution?

They are related but different. Out-of-order execution reorders instructions whose inputs are ready, while speculative execution runs instructions before it is known that they should execute at all, such as those after an unresolved branch; modern cores do both.

What is the difference between Spectre and Meltdown?

Spectre tricks the branch predictor into speculatively running legitimate code paths that leak data the victim program can access. Meltdown exploited CPUs whose speculative loads could read kernel memory before the permission check took effect, and it was largely fixed by kernel page-table isolation and later hardware changes.

Why can discarded speculative results still leak data?

The CPU discards register results but does not restore the cache, so data loaded during speculation leaves a trace that can be detected by measuring access times.
