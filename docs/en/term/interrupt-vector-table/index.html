What is Interrupt vector table?

A table listing, for each type of interrupt or exception, the start address of its handler. The CPU indexes it by the cause number to find where to begin handling.

Japanese name: 割り込みベクタテーブル

Field: OS & Hardware

How the CPU uses the table

When an interrupt or exception is accepted, hardware determines a number, called the vector, that identifies its cause: a timer, a particular peripheral, a page fault, an illegal instruction or a system call. The CPU saves the address of the next instruction and status such as the operating mode, then uses the vector as an index into the interrupt vector table, typically reading the entry at base + vector × entry size. That entry holds the handler's start address. The handler saves the registers it uses, services the event and executes a return-from-interrupt instruction.

Where the table lives

Architectures differ in detail. On Arm Cortex-M microcontrollers the table sits at the start of the code memory: its first word is the initial stack pointer, the second is the reset handler address, and later words point to fault and peripheral handlers; on most cores a vector table offset register (VTOR) lets software move it. In x86 real mode the table occupies the first 1 KB of memory with 256 four-byte entries, while protected and long modes use an interrupt descriptor table (IDT) located by the IDTR register. RISC-V uses the mtvec register, which can send all traps to one handler or vector interrupts to separate addresses.

Setting it up in embedded firmware

On a microcontroller with no operating system, the vector table must be at the address the hardware expects from the moment of reset. The startup code defines it as an array of function pointers in its own section, and the linker script places that section at the required flash address. Typical startup files give every entry a weak default handler, often an infinite loop, so the application overrides only the interrupts it uses by defining functions with matching names. A misspelled handler name therefore compiles cleanly but silently routes the interrupt to the default loop.

Vector table versus polling

A vectored scheme sends each cause straight to its own handler, so the CPU does not need to read status registers to discover what happened, which shortens interrupt latency. The alternative is a single entry point whose handler reads a cause register and dispatches in software, as RISC-V's direct mode does. On a general-purpose operating system, the kernel fills the table at boot so timer ticks, device interrupts, page faults and system calls each reach the correct kernel routine.

Answer: B. Specifying the address where handling begins for each type of interrupt or exception

When an interrupt or exception occurs, the CPU obtains a number (vector) for its cause, reads the handler's start address from the interrupt vector table and jumps there. The OS fills in the table at boot so that the timer, each device, page faults, system calls and so on can invoke separate handlers. Counting occurrences is a separate statistics mechanism, and the order of processes is managed by the OS scheduler.

FAQ

What is an interrupt vector?

An interrupt vector is the number assigned to an interrupt or exception source, used as an index into the vector table. The term is also used loosely for the table entry itself, which holds the handler address.

Where is the vector table on an ARM Cortex-M microcontroller?

By default it is at the start of the boot memory, usually flash. Its first entry is the initial stack pointer value and its second is the reset handler, and on most cores the vector table offset register (VTOR) can relocate it, for example to RAM.

What is the difference between the IVT and the IDT on x86?

The interrupt vector table (IVT) is the real-mode table of 256 segment:offset addresses at the bottom of memory. The interrupt descriptor table (IDT) replaces it in protected and long modes, holding descriptors with privilege information, and can be placed anywhere via the IDTR register.
