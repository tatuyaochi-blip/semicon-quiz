What is Relocation?

Rewriting placeholder addresses in instructions and data with correct values once final addresses are decided. The linker does it, and with dynamic linking part of it is done at run time by the dynamic linker.

Japanese name: 再配置

Why relocation is needed

Separate compilation means each source file is translated without knowing where its code and data will finally sit in memory, or where functions and variables defined in other files will be. The compiler therefore assumes each section starts at address 0 and, wherever an instruction or data word needs an address it cannot know, writes a placeholder and records a relocation entry. After the linker has laid out every section of every object file and decided final addresses, it walks these entries and writes the correct values. Without this step, independently compiled pieces could not be combined into one program.

What a relocation entry records

Each entry names the location to patch, given as an offset within a section, the symbol whose address is needed, an addend, and a type. The type tells the linker how to compute the value and how to encode it: an absolute 32- or 64-bit address, a PC-relative distance for branches and calls, or a value split across two instructions. RISC-V, for example, builds addresses with pairs such as lui plus addi or auipc plus jalr, so separate relocation types fill the upper 20 bits and the lower 12 bits.

Static and dynamic relocation

In a fully static link, the linker resolves every relocation and the executable runs as is. Shared libraries change this, because their load addresses are not fixed until run time. Position-independent code reaches global data through a table of addresses, the global offset table (GOT), and calls library functions through small stubs in the procedure linkage table (PLT). The dynamic linker fills the GOT when the program loads, or lazily on the first call. Position-independent executables loaded at randomized addresses also carry simple relative relocations that the loader applies by adding the actual base address.

Relocation versus symbol resolution

The two steps are easily confused. Symbol resolution matches each referenced name with exactly one definition, and its failures appear as undefined-reference or multiple-definition errors. Relocation comes afterwards and is purely about patching bits: once the address of every symbol is known, it writes the right numbers into the recorded fields. Relocation has failures of its own. If the computed value does not fit in the instruction field, for instance a branch target beyond its reach, the GNU linker reports relocation truncated to fit, which usually calls for a different code model or a longer instruction sequence.

The compiler builds each file as if it started at address 0 and records, as relocation entries, every place that uses the address of another file's function or of its own variables. After laying out all files and deciding real addresses, the linker computes the correct address (or PC-relative distance) for each recorded place and writes it into the instruction. With dynamic linking, part of this patching is done at run time by the dynamic linker.

FAQ

What is the difference between symbol resolution and relocation?

Symbol resolution decides which definition each referenced name refers to. Relocation then writes the final addresses or distances of those symbols into the instructions and data that use them.

What does the linker error relocation truncated to fit mean?

The linker computed an address or offset that is too large for the instruction field it must go into, such as a branch whose target is out of range. Changing the code model or memory layout, or using a longer instruction sequence, usually fixes it.

Does relocation happen at run time?

Partly. The static linker does most of it, but with shared libraries and position-independent executables the dynamic linker applies the remaining relocations when the program is loaded or when a library function is first called.
