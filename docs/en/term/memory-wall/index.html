What is Memory wall?

The problem that memory bandwidth and latency improve more slowly than processor performance, limiting overall performance. HBM, larger caches and advanced packaging are used to address it.

Japanese name: メモリウォール

Memory wall appears in 2 practice questions across 2 topics, including DRAM, Advanced packaging (3D and chiplets).

Field: DRAM

Where the gap comes from

Processor performance grew quickly for decades, first through clock speed and later through more cores and wider vector units, while DRAM was optimized mainly for density and cost per bit. DRAM access latency has stayed in the tens of nanoseconds, so at clock rates of several gigahertz a miss to main memory costs hundreds of cycles. The phrase memory wall was popularized in the mid-1990s to warn that this widening gap, not the processor core, would ultimately limit system performance.

Latency wall vs. bandwidth wall

The problem has two faces. Latency hurts code with dependent accesses, such as following pointers through a linked structure, where each load must finish before the next address is known. Bandwidth hurts streaming code that touches lots of data per operation. The roofline model captures the bandwidth side: attainable performance is the lower of peak compute and memory bandwidth multiplied by arithmetic intensity, the number of operations performed per byte moved. Code with low arithmetic intensity never reaches peak compute, however many cores are available.

Why AI workloads hit it hard

Large neural networks hold billions of weights, and generating one token at small batch sizes reads essentially every weight once while doing only a multiply and an add with each. With 16-bit weights that is about one operation per byte, while modern accelerators can perform hundreds of operations for each byte their memory delivers. The compute units therefore wait on memory. Batching requests, quantizing weights to fewer bits and keeping data on chip all raise arithmetic intensity or cut the bytes moved.

How designers push back

Multilevel caches exploit locality so most accesses never reach DRAM, and hardware prefetchers fetch data before it is requested. Out-of-order cores and GPUs with thousands of threads keep many misses in flight to hide latency. High-bandwidth memory (HBM) placed beside the processor with advanced packaging, and large caches stacked on the die, raise bandwidth directly. Processing-in-memory and near-memory computing take the opposite route, moving some computation to where the data already lives instead of moving the data.

Answer: B. The memory wall

Processor compute performance has grown rapidly, but bandwidth to memory has grown more slowly, so compute units spend more time waiting for data. This is the memory wall. It is especially severe for large AI models, which read huge numbers of weights for every computation, and advanced packaging that places HBM next to the processor, along with stacked large caches, are countermeasures.

FAQ

Is the memory wall about latency or bandwidth?

Both. Latency limits programs that make dependent memory accesses, while bandwidth limits programs that stream large amounts of data relative to the computation they do.

How does HBM help with the memory wall?

HBM stacks DRAM dies next to the processor and uses a very wide interface, giving much higher bandwidth than conventional DIMMs. It mainly attacks the bandwidth side; latency stays in the same tens-of-nanoseconds range.

Why are large language models memory-bound?

During generation at small batch sizes, each weight is fetched from memory and used for only a couple of operations. The accelerator can compute far faster than memory can supply the weights.
