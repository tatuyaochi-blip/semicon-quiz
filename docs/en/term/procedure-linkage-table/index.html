What is Procedure linkage table (PLT)?

A table of small stubs used to call shared-library functions. With lazy binding, the dynamic linker resolves the address on the first call and writes it into the GOT.

Japanese name: PLT(プロシージャリンケージテーブル)

Why calls go through a stub

A shared library can be loaded at a different address in each process, so the address of a function like printf is unknown when the program is linked. Patching every call instruction at load time would make code pages writable and unshareable between processes. Instead, the linker points each external call at a small stub in the procedure linkage table (PLT). The stub performs an indirect jump through a slot in the global offset table (GOT), a writable data area that the dynamic linker fills with real addresses.

Lazy binding step by step

With lazy binding, each GOT slot initially points back into its own PLT stub. On the first call, the stub pushes an index identifying the function's relocation entry and jumps to a common PLT header, which enters the dynamic linker's resolver. The resolver looks up the symbol in the loaded libraries, writes its address into the GOT slot and jumps to the function. Every later call goes stub, GOT, function with no further lookup. Functions that are never called are never resolved, which shortens program start-up.

Eager binding and read-only GOT

Because the GOT is writable and holds code addresses, an attacker who can overwrite memory may redirect a GOT entry to hijack control flow. Many systems therefore resolve all symbols at start-up, for example by linking with -z relro and -z now on Linux, and then mark the GOT read-only, a hardening known as full RELRO (relocation read-only). The trade-off is a slower start for programs that import many functions, in exchange for removing a common attack target.

Symbol visibility and internal calls

Exported functions in a shared library can be overridden, or interposed, by a definition with the same name in another module, so even calls from inside the library must normally go through the PLT. Giving internal functions hidden visibility removes them from the dynamic symbol table, so calls to them become direct PC-relative calls, the dynamic linker has fewer symbols to process and name clashes with other libraries are avoided. The GOT also holds addresses of external data, but data accesses read the GOT directly without a PLT stub.

With lazy binding, the first call makes the stub jump to the dynamic linker's resolver, which finds the real address and writes it into the GOT. Later calls jump directly to the address in the GOT. Skipping resolution of unused functions speeds up start-up. For security, though, resolving everything at start-up and making the GOT read-only is also widely used.

FAQ

What is the difference between the PLT and the GOT?

The PLT contains small executable stubs that external calls jump to, while the GOT is a data table holding the resolved addresses; each PLT stub jumps indirectly through its GOT entry.

What is lazy binding in dynamic linking?

Lazy binding defers resolving a shared-library function's address until the first time it is called, when the dynamic linker looks it up and stores it in the GOT for all later calls.

What does full RELRO do?

It makes the dynamic linker resolve all symbols at start-up and then remaps the GOT read-only, so attackers cannot overwrite GOT entries to redirect function calls.
