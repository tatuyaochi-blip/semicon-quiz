What is Root of trust?

The component unconditionally trusted as the starting point of security checks, such as immutable ROM boot code and a public key inside the chip.

Japanese name: ルートオブトラスト

Field: Hardware Security

Why a starting point of trust is needed

In secure boot, each stage verifies the signature of the next software before starting it, building a chain of trust. But the very first checker cannot be checked by anything else. This starting point, which must be trusted without verification, is the root of trust. If it is tampered with, every later check becomes meaningless. A root of trust is therefore kept as small and simple as possible to minimize bugs, placed where it cannot be rewritten, and protected from being read or written from outside.

Implementation in silicon

A typical setup is boot code in mask ROM, fixed at manufacture and unchangeable, plus the public key used to verify signatures. To save space, the key's hash is often stored in one-time-programmable eFuses. Per-device secret keys are written into eFuses or OTP memory, or derived from manufacturing variation using a PUF. High-end SoCs increasingly include a security subsystem combining a dedicated processor, crypto engines, a true random number generator and key storage, which boots before the main CPU and verifies the startup of everything else. Open designs such as OpenTitan and Caliptra also exist.

Classification by role

Roots of trust are sometimes divided by the role they play. The TCG (Trusted Computing Group) distinguishes the root of trust for measurement (RTM), which first measures the software being booted; the root of trust for storage (RTS), which keeps keys and measurements safe; and the root of trust for reporting (RTR), which signs measurements and reports them externally. There is also a root of trust for verification, which checks signatures in secure boot. On PCs, the CPU or the first part of the firmware typically serves as the measurement root, while the TPM serves as the storage and reporting root. A single chip does not necessarily fill every role.

Weaknesses and protections

Boot ROM's strength is that it cannot be rewritten, but if a vulnerability is found there, shipped products cannot be fixed. ROM code is therefore kept small and verified thoroughly. Against fault-injection attacks, which apply momentary glitches to the supply voltage or clock to skip the signature check, designs perform checks twice or add glitch-detection circuits. These are combined with disabling debug ports such as JTAG before shipment, preventing rollback to older versions, and storing hashes of several keys in eFuses so that a leaked key can be revoked.

FAQ

What is a root of trust?

It is the part trusted without verification as the starting point of security checks. Unchangeable ROM boot code, the public key used to check signatures and device-unique keys are placed in the chip, and the chain of trust is built from there.

Why must it be in hardware?

A starting point built only in software could be rewritten by an attacker who has taken over the OS or firmware. Using hardware properties such as ROM and eFuses fixed at manufacture and key storage that cannot be read from outside keeps the starting point safe even if software is compromised.

Is a TPM a root of trust?

A TPM serves as the root for storing keys and measurements and the root for signing and reporting measurements. However, the software being booted is usually first measured by the CPU or the first part of the firmware, so a TPM alone does not provide every root of trust.
