What is Clock uncertainty?

A margin subtracted from the available time in timing analysis to account for jitter and for clock skew not yet known. It is set with set_clock_uncertainty in SDC, and before the clock tree is built it is set larger to cover skew as well.

Japanese name: クロックの不確かさ

Clock uncertainty appears in 4 practice questions across 2 topics, including Timing analysis and CDC, IC design flow and EDA.

Field: Timing analysis and CDC

How it enters the timing checks

In static timing analysis, clock uncertainty is a user-specified margin that makes setup and hold checks stricter. For setup, it is subtracted from the time available before the capturing edge: with a 1.25 ns period, 0.05 ns setup time and 0.05 ns uncertainty, data must arrive by 1.15 ns. For hold, it is added to the hold requirement, so data must stay stable for longer after the edge. It is specified in SDC (Synopsys Design Constraints) with commands such as set_clock_uncertainty -setup 0.05 [get_clocks clk], with a separate -hold value.

What the margin covers

Three ingredients are usually folded in. Jitter from the phase-locked loop (PLL) and clock distribution makes edges arrive early or late from cycle to cycle. Before clock tree synthesis (CTS), clocks are ideal and skew between flip-flops is unknown, so an estimate of it is added. Many teams also add a design margin for effects not modeled precisely at that stage, such as supply noise. Period jitter matters for setup, which spans two different edges, but almost cancels for hold, where launch and capture use the same edge; the skew estimate applies to both.

How the value changes through the flow

During synthesis and placement, with ideal clocks, uncertainty is set relatively large to cover jitter plus expected skew. After CTS the clocks become propagated: the tool computes each flip-flop's actual clock latency, so skew is analyzed explicitly and is removed from the uncertainty, leaving jitter and margin. Uncertainty can also be set between specific clock pairs with -from and -to options, for example for paths between related clocks generated by different PLL outputs. Too large a value over-constrains the design and costs area and power; too small risks failures in silicon.

Uncertainty vs. skew and derating

Skew is a computed difference between the clock arrival times at two flip-flops, known only once a clock tree exists. Clock uncertainty is not computed; it is an assumed lump margin applied to every path of that clock. On-chip variation (OCV) derating is different again: it scales cell and wire delays by factors, making the launch path slower and the capture path faster, or vice versa, rather than subtracting a fixed time. A complete signoff setup typically combines propagated skew, derating and a small remaining uncertainty.

Try it: questions about Clock uncertainty

On a flip-flop-to-flip-flop path, the clock-to-output delay is 0.15 ns, the maximum combinational logic delay is 2.2 ns and the setup time is 0.15 ns. Ignoring skew and clock uncertainty, what is the maximum clock frequency at which this path can operate?

  1. AAbout 425 MHz
  2. BAbout 455 MHz
  3. C400 MHz
Show answer and explanation

Answer: C. 400 MHz

The minimum clock period is the sum of the clock-to-output delay, the combinational logic delay and the setup time. 0.15 + 2.2 + 0.15 = 2.5 ns, so the maximum frequency is 1 ÷ 2.5 ns = 400 MHz. About 425 MHz comes from 2.35 ns, which leaves out the setup time, and about 455 MHz from the 2.2 ns combinational logic delay alone. The maximum frequency of the whole chip is set by the tightest of such paths, the critical path.

On a path with a clock period of 1.25 ns (800 MHz), the clock-to-output delay plus combinational logic delay totals 1.05 ns, the setup time is 0.05 ns, and the setup clock uncertainty is set to 0.05 ns. What is the setup slack?

  1. A0.15 ns
  2. B0.20 ns
  3. C0.10 ns
Show answer and explanation

Answer: C. 0.10 ns

Clock uncertainty is a margin subtracted from the available time to account for jitter and skew that is not yet determined. The required time is 1.25 − 0.05 (uncertainty) − 0.05 (setup time) = 1.15 ns and the arrival time is 1.05 ns, so the slack is 0.10 ns. 0.15 ns leaves out the uncertainty, and 0.20 ns subtracts neither the setup time nor the uncertainty. Before place and route there is no clock tree, so it is common to set a larger uncertainty that also covers skew.

FAQ

Does clock uncertainty apply to hold checks?

Yes, but it is set separately with set_clock_uncertainty -hold and is usually smaller, because period jitter largely cancels when launch and capture share the same edge. Before CTS it still includes the expected skew.

Why is clock uncertainty reduced after clock tree synthesis?

Once the clock tree exists, the tool calculates real clock skew from the tree's delays, so the part of the margin that estimated skew is no longer needed. Only jitter and any design margin remain.

How do I calculate setup slack with clock uncertainty?

Required time equals the clock period minus setup time minus uncertainty (adjusted for clock latencies), and slack is required time minus data arrival time. For example, 1.25 − 0.05 − 0.05 = 1.15 ns required versus 1.05 ns arrival gives 0.10 ns slack.
