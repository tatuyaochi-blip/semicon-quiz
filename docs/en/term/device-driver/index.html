What is Device driver?

An OS component that operates a specific peripheral. It handles the device's registers and interrupts and lets applications use the device through a common interface.

Japanese name: デバイスドライバ

What a driver actually does

A driver translates generic requests from the kernel into the exact sequence a particular device expects. At start-up it probes the device, maps its registers into the address space (memory-mapped I/O) and puts the hardware into a known state. During operation it writes command and status registers, prepares DMA (direct memory access) descriptors so the device can move data to and from memory without the CPU copying it, and services the interrupts the device raises when work completes. Upward it plugs into a common framework, such as a block, network or character-device interface, so applications see ordinary reads, writes and control calls.

Interrupt handling and deferred work

Interrupt handlers run while normal work on that CPU is suspended, so drivers keep them short: acknowledge the device, note what happened and schedule the rest. The heavier processing, such as passing received packets up the protocol stack or completing a disk request, runs later in a context that can be scheduled. This split is often called top half and bottom half. Very high-rate devices such as fast network cards may switch from one interrupt per event to polling under load, because taking an interrupt for every packet would waste more CPU time than checking a queue in a loop.

Why driver bugs are dangerous

Most drivers run in kernel mode with the same privileges as the rest of the kernel. A stray pointer, a missed lock or a DMA buffer programmed with the wrong address can therefore corrupt memory anywhere or crash the whole system rather than just one program. For this reason drivers are a common source of system instability and security flaws. Some designs move drivers into user-space processes, trading extra context switches for isolation, and an IOMMU can limit which memory a device is allowed to reach even when its driver misbehaves.

Driver vs. firmware vs. hypervisor

Firmware is code that runs on the device itself, for example on a controller inside an SSD or a network card; the driver runs on the host CPU and talks to that firmware through registers and shared memory. A hypervisor sits below whole operating systems and shares hardware among virtual machines. Inside a virtual machine, the guest either uses paravirtual drivers that talk efficiently to the hypervisor, or, with device assignment, runs the ordinary driver for a real device handed to it.

Answer: A. Handling device-specific operations behind a common interface

Each device has its own register layout and operating procedure. A device driver is the OS component that absorbs these differences: it initializes the device, reads and writes registers, sets up DMA and handles interrupts, while offering upper layers a common interface such as file-style reads and writes. Applications can then use devices without knowing their details. Circuit design and screen appearance are not a driver's job.

FAQ

Is a device driver part of the operating system?

Usually yes. Most drivers are kernel modules that run with kernel privileges and plug into the OS's device frameworks, although some systems also support drivers that run as user-space processes.

What is the difference between a driver and firmware?

Firmware runs on a processor inside the device and controls the hardware directly. The driver runs on the host CPU as part of the OS and communicates with the device and its firmware through registers, DMA buffers and interrupts.

Why can a bad driver crash the whole computer?

Kernel-mode drivers share the kernel's address space and privileges, so a bug can overwrite any kernel data or leave hardware in an inconsistent state. A user program's bug, by contrast, is confined to its own process.
