What is Position-independent code?

Machine code that runs without modification at any load address, also called PIC. It uses PC-relative references and the GOT and is used for shared libraries and PIEs.

Japanese name: 位置独立コード

How PIC addresses code and data

Position-independent code (PIC) never embeds absolute addresses in its instructions. Branches and calls name their targets as distances from the program counter, which stay the same wherever the whole module is placed. For targets farther than a branch field can reach, RISC-V pairs auipc, which adds a 20-bit immediate shifted left by 12 bits to the PC, with jalr or a load that supplies the low 12 bits, covering about ±2 GiB from the current instruction. x86-64 offers RIP-relative addressing for the same purpose, which makes position-independent code nearly as fast as fixed-address code.

The GOT and PLT

PC-relative distances work within one module, but the address of a variable or function in another shared library is not known until run time. PIC therefore reaches such symbols through the global offset table (GOT), a per-module table of addresses placed at a fixed distance from the code. The code loads the needed address from the GOT, and the dynamic linker fills in the real addresses at load time. On ELF systems, calls to external functions additionally go through small stubs in the procedure linkage table (PLT), which can resolve each function lazily on its first call.

Why shared libraries need it

A shared library may be mapped at a different virtual address in every process that uses it. If its code contained absolute addresses, the loader would have to patch the instructions for each address, turning shared read-only pages into private writable copies and defeating the purpose of sharing. With PIC, only the small writable GOT differs between processes, so the code pages need no changes and a single physical copy is mapped into all of them. This saves memory and lets the library load quickly no matter where it lands.

PIC vs. PIE and the security link

A position-independent executable (PIE) applies the same technique to the main program, typically built with the -fPIE and -pie options in GCC or Clang, while shared libraries use -fPIC. Older executables assumed a fixed load address, so address space layout randomization (ASLR) could move libraries and the stack but not the main program's code, leaving its addresses predictable to attackers. A PIE can be loaded anywhere, so its code is randomized too, and many current Linux distributions build PIEs by default. The cost is a small overhead from GOT indirection, which was noticeably larger on 32-bit x86.

A shared library may be loaded at a different address in each process. Position-independent code refers to functions and data not by fixed addresses but by distances from the PC or through a table of addresses (the GOT). Then the code pages need no patching when the load address changes, so one copy in physical memory can be shared by many processes.

FAQ

What does PIC stand for?

PIC stands for position-independent code, machine code that runs correctly without modification at any load address. It relies on PC-relative addressing and the global offset table.

What is the difference between -fPIC and -fPIE?

Both generate position-independent code; -fPIC is meant for shared libraries, whose symbols may be overridden by other modules, while -fPIE targets the main executable and can use slightly cheaper direct references to its own symbols. An executable built with -fPIE is linked with -pie to produce a PIE.

Why is the global offset table needed?

Code cannot embed the address of a symbol in another module, because that address is only known after loading. The GOT holds those addresses, filled in by the dynamic linker, and the code reaches the GOT through a PC-relative reference.
