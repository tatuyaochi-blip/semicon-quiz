What is Address space layout randomization (ASLR)?

A countermeasure that changes the addresses of the stack, heap, shared libraries and executable every run so attackers cannot easily predict them.

Japanese name: ASLR

How ASLR shifts a process

When a program starts, the kernel and the dynamic loader choose random, page-aligned base offsets for each major region of the address space: the stack, the heap, the mmap area where shared libraries are mapped, and the executable itself if it was built as a position-independent executable (PIE). The relative order of the regions stays the usual one (text, data, BSS and heap at low addresses, stack at the top), but their absolute addresses differ on every run. Address space layout randomization (ASLR) therefore changes where things are, not what the program does.

Why attackers need addresses

Memory-corruption exploits such as stack buffer overflows usually overwrite a return address or function pointer with the address of something useful: shellcode on the stack, a library function like system() in a return-to-libc attack, or a chain of instruction snippets in return-oriented programming (ROP). Each of these needs exact addresses. With ASLR the attacker must guess them, and a wrong guess typically crashes the process instead of handing over control. The protection is probabilistic, so its strength depends on how many random bits are available, which is much more limited on 32-bit address spaces than on 64-bit ones.

PIE and position-independent code

ASLR can only move code that does not assume a fixed load address. Shared libraries have long been compiled as position-independent code (PIC), reaching their data through PC-relative addressing and the global offset table (GOT). Older executables, however, were linked for a fixed address, so the main program's code stayed at a known location and gave attackers a reliable source of ROP gadgets. Building with -fPIE and -pie makes the executable relocatable as well, so the loader can randomize it too. On x86-64 the cost is small because PC-relative data access is native.

Limits and companion defences

Randomization is applied per region, so leaking a single pointer from a library reveals the offset of that whole library, and from there every function in it. Child processes created by fork() inherit the parent's layout, which lets attackers probe a forking server repeatedly. For these reasons ASLR is combined with non-executable writable memory (W^X or NX), stack canaries and control-flow protections. The operating-system kernel can be randomized too, which is called KASLR. On Linux the setting is visible in /proc/sys/kernel/randomize_va_space.

Answer: A. To change the addresses of the stack, heap, libraries and so on every run, making target addresses hard for attackers to predict

Attacks that exploit bugs such as buffer overflows depend on knowing the addresses of library functions or data on the stack. ASLR shifts where the stack, heap, shared libraries and the executable are placed every time a process starts, so attackers cannot hard-code addresses. It is not a complete defence on its own and is combined with other measures such as separating writable and executable memory.

FAQ

Does ASLR prevent buffer overflow attacks?

No. ASLR does not stop the overflow itself; it only makes it hard to know which address to jump to, so most attempts crash instead of succeeding. An information leak that reveals one real address can defeat it, which is why it is paired with NX memory and stack canaries.

What is the difference between ASLR and PIE?

ASLR is the operating-system mechanism that loads memory regions at random addresses on each run. PIE is a way of compiling and linking the executable so that its code works at any address, which allows ASLR to randomize the main program as well as libraries, stack and heap.

How do I check whether ASLR is enabled on Linux?

Read /proc/sys/kernel/randomize_va_space: 0 means disabled, 1 randomizes the stack, mmap region and shared libraries, and 2 additionally randomizes the brk-based heap. Most distributions default to 2.
