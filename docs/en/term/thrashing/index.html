What is Thrashing?

A state in which physical memory is so short that pages are constantly evicted and reloaded, and little useful work gets done. It is relieved by running fewer processes or adding memory.

Japanese name: スラッシング

Thrashing appears in 2 practice questions across 1 topic, including OS & Hardware.

Field: OS & Hardware

Why it happens

Each process has a working set, the pages it actively uses over a short time window. When the combined working sets of all running processes exceed physical memory, loading a page for one process evicts a page that another, or the same, process will need almost immediately. That page then faults back in, evicting yet another needed page. Page faults go to disk or SSD, which takes from tens of microseconds to milliseconds, compared with around 100 ns for DRAM, so the system spends nearly all its time waiting for paging I/O.

The feedback trap

A classic textbook scenario shows how thrashing can feed itself. As processes wait on page faults, CPU utilization drops. A naive scheduler that tries to raise utilization by admitting more processes shrinks the memory available to each one, causing even more faults and lower utilization. Throughput collapses rather than degrading gracefully. The symptoms are a very high page-fault rate, saturated swap I/O, high time spent waiting on I/O and little useful computation, even though the machine appears busy.

Remedies

The fundamental cure is to make memory demand fit: run fewer processes at once by suspending or swapping out entire processes, or add physical memory. Working-set based policies admit a process only when its working set can be held. Page-fault-frequency control gives a process more frames when its fault rate exceeds an upper threshold and takes frames away when it falls below a lower one. Programs can help themselves by improving locality so their working sets are smaller.

Thrashing vs. related terms

Thrashing is a sustained throughput collapse due to memory shortage. It differs from Bélády's anomaly, the specific case where FIFO replacement produces more faults when given more frames; stack algorithms such as LRU cannot show that anomaly. It also differs from deadlock, where tasks stop because each waits for resources another holds. The word is also used for caches and TLBs: cache thrashing describes lines repeatedly evicting each other, often addresses mapping to the same set, which is the same pattern at a smaller scale.

With FIFO page replacement, adding physical pages can sometimes increase page faults. What is this phenomenon called?

  1. AThrashing
  2. BBélády's anomaly
  3. CCopy-on-write

Answer: B. Bélády's anomaly

Intuitively, more physical pages should mean fewer page faults, but with FIFO certain access sequences are known to fault more when the page count grows from three to four. This is Bélády's anomaly. It cannot occur with stack algorithms such as LRU, where the set of pages held with more frames always contains the set held with fewer. Thrashing is constant replacement from memory shortage, and copy-on-write copies pages on write.

Answer: C. Thrashing

When the combined working sets of running processes exceed physical memory, loading a needed page evicts a page another process needs, which is then needed again almost immediately. Time is spent waiting on disk I/O and CPU utilization falls. This is thrashing, relieved by running fewer processes or adding memory. Deadlock is when tasks stop because each waits for resources held by the other.

FAQ

What causes thrashing in an operating system?

Running processes whose combined working sets exceed physical memory, so pages are evicted and then needed again almost immediately, keeping the system busy with paging I/O instead of useful work.

How do you stop thrashing?

Reduce the number of active processes, add physical memory, or use working-set or page-fault-frequency policies that allocate frames according to each process's actual needs.

What is the difference between thrashing and Bélády's anomaly?

Thrashing is performance collapse from memory overcommitment, while Bélády's anomaly is the counterintuitive case where FIFO replacement causes more page faults when more frames are available.
