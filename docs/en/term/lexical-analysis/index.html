What is Lexical analysis?

The first compiler phase, which splits the characters of source code into tokens such as identifiers, numbers, operators and keywords. Whitespace and comments are removed here.

Japanese name: 字句解析

Field: Compilers

From characters to tokens

The lexical analyzer, or lexer, reads source text character by character and groups it into tokens, each with a type and often a value. For count = count + 1; it produces identifier count, operator =, identifier count, operator +, number 1 and the semicolon. Whitespace and comments are dropped, identifiers may be entered into a symbol table, and line numbers are recorded so later phases can report errors precisely. The parser then works only with the token stream.

Regular expressions and finite automata

Token patterns are written as regular expressions, for example a letter followed by letters or digits for identifiers and one or more digits for integers. These can be converted into a nondeterministic finite automaton, then into a deterministic one (DFA) that changes state on each character, so the lexer runs in time proportional to input length. Generator tools such as lex and flex build this automaton automatically from a list of patterns, although many production compilers use hand-written lexers.

Resolving ambiguity

Two rules settle which token to produce. Longest match, also called maximal munch, takes the longest string that matches any pattern, so >= becomes one token rather than > followed by =, and ifx is an identifier rather than the keyword if followed by x. When two patterns match the same longest string, the one listed first wins, which is how keywords take priority over the general identifier pattern.

Lexical analysis vs. parsing

Regular expressions cannot count nesting, so they cannot check matched parentheses or if statements inside if statements. That job belongs to parsing, which uses a context-free grammar to build a syntax tree from the tokens. Lexical errors are things like an illegal character or an unterminated string literal; a missing semicolon or unbalanced bracket is a syntax error found by the parser, and an undeclared variable is caught later by semantic analysis.

Answer: B. Splitting the characters of source code into tokens such as identifiers and operators

Lexical analysis is the first phase of a compiler. It splits, for example, "count = count + 1;" into the tokens identifier count, symbol =, identifier count, symbol +, number 1 and symbol ;. Whitespace and comments are discarded here. Token rules can be written as regular expressions, so a finite automaton processes them quickly. Checking grammar in tree form is the next phase, parsing, and checking types and names is semantic analysis.

Answer: B. Regular expressions, processed by finite automata

Token types can be written concisely as regular expressions, such as "a letter followed by letters or digits" for identifiers and "one or more digits" for numbers. Regular expressions convert to finite automata, machines with a finite number of states that change state with each character read, so tokens are extracted in time proportional to input length. Lexers are therefore often generated automatically from regular expressions by tools. Rounding and cache rules have nothing to do with lexical analysis.

FAQ

What is the difference between a lexer and a parser?

A lexer turns characters into tokens using regular patterns, while a parser checks the token sequence against a context-free grammar and builds a syntax tree.

What is a token in a compiler?

A token is the smallest meaningful unit of source code, such as an identifier, keyword, number, operator or punctuation mark, usually stored as a type plus its text or value.

What is the maximal munch rule?

It is the lexer rule of always taking the longest possible match, so that inputs such as ++ or >= become single tokens instead of being split.
