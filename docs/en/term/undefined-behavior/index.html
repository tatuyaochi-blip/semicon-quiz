What is Undefined behavior?

Behavior for which the C or C++ standard imposes no requirements. Examples are signed integer overflow, reading or writing outside an array, dereferencing a null pointer, using freed memory and left-shifting a negative value. A compiler may optimize on the assumption that a correct program never has undefined behavior, so such code may happen to work as expected, or may give unexpected results, for example a check disappearing under some optimization settings. It is distinguished from implementation-defined behavior, which the implementation chooses and documents.

Typical examples

Examples include overflow in signed integer arithmetic (such as INT_MAX + 1), reading or writing outside an array, using the value of an uninitialized automatic variable, reading or writing through a null or dangling pointer, freeing the same memory twice, integer division by 0, and shifting by the type width or more or left-shifting a negative value. Overflow of unsigned integers is not undefined behavior; it is defined to wrap around modulo a power of 2.

Relation to compiler optimization

Because the compiler may assume that undefined behavior never happens, it may treat x + 1 > x as always true, or delete a p == NULL check that comes after *p has been read. So a program that worked as expected at -O0 can stop working just by switching to -O2 or upgrading the compiler. This is not a compiler bug; the cause is that the program breaks an assumption of the standard.

Finding and preventing it

With gcc or clang, -fsanitize=undefined (UBSan) detects signed integer overflow and similar errors at run time, and -fsanitize=address (ASan) detects out-of-bounds accesses and use after free. Warnings from -Wall and -Wextra, static analysis tools and coding rules such as MISRA C also help reduce undefined behavior.

Answer: A. Behavior the standard places no requirements on; the compiler may optimize assuming it never happens, so results can be unexpected

Undefined behavior is behavior on which the standard imposes no requirements, such as signed integer overflow, out-of-bounds array access, null pointer dereference and use after free. It may happen to work as expected, but because the compiler may optimize on the assumption that it "does not happen in a correct program", merely changing optimization settings or the compiler version can change the result. In contrast, things such as the size of int and whether char is signed, which the implementation decides and must document, are called implementation-defined behavior. With gcc and clang, -fsanitize=undefined detects some undefined behavior at run time.

  2. BShifting a negative int value right by 1 bit with >>
  3. CAdding 1 to an int variable whose value is the maximum 2147483647

Answer: C. Adding 1 to an int variable whose value is the maximum 2147483647

A signed integer operation whose result exceeds the representable range, such as 2147483647 + 1 in int, is undefined behavior. Unsigned integer arithmetic is defined to wrap modulo 2³², so 4294967295 + 1 gives 0 and is not undefined behavior. Right-shifting a negative value is implementation-defined behavior, where the implementation decides whether it is an arithmetic or a logical shift; gcc uses an arithmetic shift. On the other hand, left-shifting a negative value is undefined behavior.

FAQ

What is the difference between undefined behavior and implementation-defined behavior?

Implementation-defined behavior, such as the size of int, whether char is signed, or the result of right-shifting a negative value, is behavior for which the implementation chooses one option and documents it. Undefined behavior is behavior on which the standard imposes no requirements, and the result may differ from case to case even with the same implementation. Portable programs make any reliance on implementation-defined behavior explicit and avoid undefined behavior altogether.

If code with undefined behavior works, is it a problem?

Yes. Even if it happens to work as expected in the current environment, a change in optimization settings, the compiler version or the surrounding code can give a different result. From a security point of view as well, undefined behavior such as out-of-bounds writes can be exploited by attackers.
