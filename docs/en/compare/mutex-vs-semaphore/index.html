Mutex vs Semaphore: Differences Explained

A mutex protects a critical section so that only one thread at a time can use a shared resource, and the thread that locked it must be the one that unlocks it. A semaphore is a counter: it controls how many threads can use a limited resource, and it can also be used to signal events from one thread to another. A mutex is about ownership and exclusion; a semaphore is about counting and signaling.

AspectMutexSemaphore
PurposeMutual exclusion: one thread at a time in a critical sectionCounting: limit access to a pool of N resources, or signal events between threads
ValueLocked or unlocked (binary)A non-negative integer count (a binary semaphore is the special case of 0 or 1)
OwnershipOwned by the thread that locked it, and that thread should unlock itNo owner: any thread can post or signal
OperationsLock and unlockWait (P, decrement) and post (V, increment)
Signaling between threadsNot intended for itYes: for example a producer signaling a consumer
Priority inversionOften avoided with priority inheritanceUsually not supported
Typical usesProtecting a shared data structure such as a list or a counterLimiting a connection pool, bounded producer-consumer buffers, signaling from an interrupt handler to a task
Common pitfallsDeadlock from inconsistent lock order, or forgetting to unlockLost signals and deadlock when counts do not match

Figures are typical orders of magnitude and vary by process generation and product.

When to use which

Mutex
When several threads touch the same data and only one may do so at a time.
Semaphore
When you need to limit how many threads use a resource, or to wake a thread when something happens.
