Interrupt vs Polling: Differences and When to Use Each

There are two ways for a processor to learn that a device needs attention. With polling, the CPU keeps checking the device status in a loop. With interrupts, the device signals the CPU, which pauses what it is doing, runs a small handler and then resumes. Polling is simple and predictable but wastes time; interrupts are efficient and responsive but add overhead and make the program harder to reason about.

AspectPollingInterrupt
How it worksThe CPU repeatedly reads a status register to see whether the device is readyThe device raises a signal; the CPU suspends its work and runs an interrupt handler (ISR)
CPU use while waitingBusy: the CPU spends cycles checkingFree: the CPU can do other work or sleep
Response timeSet by how often the loop checks; predictableFast (microseconds), but varies with masking, priority and context saving
OverheadConstant, even when nothing happensA cost per event; a very high event rate can overwhelm the CPU (interrupt storm)
ComplexitySimple to write and debugMore complex: handlers must be short, and shared data with the main code needs care (volatile, atomic access)
PowerKeeps the CPU awakeAllows low-power sleep until an event wakes the CPU
Timing behaviorEasy to reason aboutConcurrency bugs are possible between handler and main code
Typical usesVery fast or continuous events, simple programs, high-speed networking driversTimers, buttons, communication events, sensor alerts, waking from sleep

Figures are typical orders of magnitude and vary by process generation and product.

When to use which

Polling
When events are frequent or the loop is simple, and you want predictable timing without handler complexity.
Interrupt
When events are rare or unpredictable, you want a quick response and low power, and the CPU has other work to do.
Hybrid
Some systems combine them: an interrupt announces the first event, and the driver then polls while traffic is heavy, as in high-speed network drivers.
