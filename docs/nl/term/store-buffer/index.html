Wat is Store buffer?

Kleine buffer waarin een core schrijfacties tijdelijk verzamelt. Het kan naar de volgende instructie gaan zonder te wachten op de voltooiing van het schrijven, maar voor andere cores lijkt het schrijven vertraagd.

Japanse benaming: ストアバッファ

“Store buffer” komt voor in 3 oefenvragen uit 1 onderwerpen, bijv. Multicore en synchronisatie.

Vakgebied: Multicore en synchronisatie

Waarom cores hun stores bufferen

Wanneer een core een store uitvoert, kan de doelcacheline ontbreken of door een andere core worden vastgehouden, en het verkrijgen van schrijfeigendom via het coherentieprotocol kan veel cycli kosten. In plaats van te stallen, plaatst de core adres en data in een store buffer en gaat hij verder met uitvoeren. Entries worden later naar de L1-cache weggeschreven, op x86 doorgaans in programmavolgorde. In out-of-orderprocessors bevat de store buffer ook speculatieve stores, die pas naar de cache mogen worden geschreven wanneer de store-instructie commit en vaststaat dat ze niet wordt geannuleerd.

Store-to-load forwarding

Omdat recente stores nog in de buffer kunnen staan, controleert elke load de buffer op een overeenkomend adres. Vindt hij er een, dan neemt de load de data uit de nieuwste overeenkomende entry in plaats van uit de cache, een mechanisme dat store-to-load forwarding heet. Zo blijft het single-threaded gedrag intact: een core ziet zijn eigen schrijfacties altijd direct, in programmavolgorde. Forwarding werkt het best wanneer de load precies de bytes leest die één eerdere store heeft geschreven; gedeeltelijke overlappingen tussen een load en gebufferde stores dwingen de load vaak te wachten tot die stores zijn weggeschreven.

Waarom andere cores schrijfacties laat zien

Andere cores kunnen niet in de store buffer van een core kijken, dus een gebufferde schrijfactie is voor hen onzichtbaar totdat die is weggeschreven. Neem x en y allebei 0, waarbij core 1 x = 1 en daarna r1 = y uitvoert, en core 2 y = 1 en daarna r2 = x. Onder sequentiële consistentie moet ten minste één load 1 zien. Met store buffers kunnen beide stores in hun buffers wachten terwijl beide loads 0 uit de caches lezen, zodat r1 = r2 = 0 op echte x86-machines voorkomt. Een memory barrier tussen de store en de load, die wacht tot de buffer leeg is, verbiedt dit resultaat.

Store buffers en geheugenconsistentiemodellen

Het x86-model, total store order (TSO), beschrijft in wezen een first-in-first-out-store buffer: stores blijven geordend ten opzichte van stores en loads ten opzichte van loads, en alleen een latere load naar een ander adres kan een eerdere store lijken in te halen. Zwakkere modellen zoals die van Arm en RISC-V laten onder meer ook toe dat stores buiten volgorde zichtbaar worden, dus daar zijn vaker fences of acquire/release-instructies nodig. Programmeurs vertrouwen normaal op atomaire bewerkingen op taalniveau, die de compiler op de juiste fences afbeeldt.

Antwoord en toelichting tonen

Antwoord: C. In welke volgorde de lees- en schrijfacties van een core naar meerdere adressen voor andere cores zichtbaar kunnen zijn

Voor betere prestaties kan een CPU de volgorde van geheugenbewerkingen wijzigen, bijvoorbeeld door schrijfacties in een store buffer te verzamelen of lezen voor te trekken. Binnen één core is dit zo gemaakt dat het resultaat niet verandert, maar voor andere cores kan de volgorde verwisseld lijken. Het geheugenconsistentiemodel legt vast welke verwisselingen kunnen optreden en is de afspraak waarmee programmeurs correcte synchronisatie kunnen schrijven.

Welke eigenschap van het geheugenconsistentiemodel van x86 (TSO, Total Store Order) is juist?

  1. AHet is het zwakste model dat verwisseling van alle combinaties van lezen en schrijven toestaat
  2. BHet is gewoon sequentiële consistentie, die geen enkele verwisseling toestaat
  3. CHet is een relatief sterk model dat alleen toestaat dat een leesactie van een ander adres na een schrijfactie eerder zichtbaar wordt dan die schrijfactie
Antwoord en toelichting tonen

Antwoord: C. Het is een relatief sterk model dat alleen toestaat dat een leesactie van een ander adres na een schrijfactie eerder zichtbaar wordt dan die schrijfactie

Bij TSO blijven de volgorde van schrijfacties onderling, van leesacties onderling en van een schrijfactie na een leesactie behouden, en kan alleen een leesactie van een ander adres na een schrijfactie die inhalen. Dit is een model dat de aanwezigheid van de store buffer rechtstreeks weergeeft. Veel programma's werken binnen dit bereik intuïtief, dus bij x86 zijn barrières in relatief weinig situaties nodig.

Veelgestelde vragen

Wat is store-to-load forwarding?

Het is wanneer een load een overeenkomende eerdere store vindt die nog in de store buffer wacht en de data daar direct uit haalt, zodat de core zijn eigen openstaande schrijfacties ziet zonder te wachten tot ze de cache bereiken.

Waarom kunnen beide threads 0 lezen in de store-buffering-litmustest?

De schrijfactie van elke core staat in zijn eigen store buffer, onzichtbaar voor de andere core, terwijl de volgende load de oude waarde uit de cache leest; een memory fence tussen de store en de load voorkomt dit.

Hoe hangt de store buffer samen met TSO?

Total store order is in wezen het gedrag van een FIFO-store buffer: de enige herordening die het toestaat, is dat een latere load naar een ander adres wordt voltooid voordat een eerdere store zichtbaar wordt.
