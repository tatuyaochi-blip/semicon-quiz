Wat is JIT-compilatie (just-in-time)?

Methode waarbij tijdens de uitvoering van het programma vaak uitgevoerde delen naar machinecode worden gecompileerd. Maakt optimalisatie op basis van runtime-informatie mogelijk. Wordt gebruikt in onder meer Java- en JavaScript-runtimes.

Japanse benaming: JITコンパイル

“JIT-compilatie (just-in-time)” komt voor in 3 oefenvragen uit 2 onderwerpen, bijv. Compilers, Halfgeleiderindustrie en markt.

Vakgebied: Compilers

Uitvoering in tiers

Een typische JIT-runtime (just-in-time) begint met het interpreteren van bytecode, wat vooraf niets kost maar traag draait. Tijdens het interpreteren telt hij hoe vaak elke methode wordt aangeroepen en elke lus itereert. Code die een drempel overschrijdt, gaat naar een snelle baselinecompiler, en code die hot blijft, wordt later opnieuw gecompileerd door een optimaliserende compiler die veel meer tijd per functie besteedt. Langlopende lussen kunnen midden in de uitvoering naar gecompileerde code worden overgezet, een techniek die on-stack replacement heet. Compilatie gebeurt meestal op achtergrondthreads, zodat het programma intussen blijft draaien.

Speculatie en deoptimalisatie

De interpreter en de baselinecode verzamelen profielen: welke takken worden genomen, welke objecttypes bij elke aanroeplocatie voorkomen, of integers ooit zijn overgelopen. De optimaliserende compiler gokt op deze waarnemingen, bijvoorbeeld door de ene methode te inlinen die een virtuele aanroep altijd heeft bereikt en code weg te laten voor types die nooit zijn gezien. Elke gok wordt beschermd door een goedkope guard. Faalt een guard, dan deoptimaliseert de runtime: hij reconstrueert het beeld van de interpreter van het huidige frame, gaat verder in tragere code en kan later opnieuw compileren met de nieuwe informatie. Ahead-of-time-compilers kunnen niet zo vrij op zulke gokken inzetten.

JIT versus AOT versus interpreter

Een pure interpreter start onmiddellijk en heeft tijdens de uitvoering geen compiler nodig, maar voert elke bewerking traag uit. AOT-compilatie (ahead-of-time) produceert machinecode voordat het programma draait, wat een snelle opstart, voorspelbare prestaties en geen compiler in het geheugen oplevert, maar moet optimaliseren zonder de werkelijke invoer te kennen, tenzij profile-guided optimization gegevens uit trainingsruns aanlevert. Een JIT betaalt met opwarmtijd, CPU-tijd voor compilatie en geheugen voor de codecache, en kan daarvoor in ruil bij langlopende programma's een hoge piekprestatie halen. Veel runtimes combineren benaderingen, bijvoorbeeld door opstartcode te cachen of AOT te compileren.

Praktische beperkingen

Een JIT schrijft machinecode naar het geheugen en voert die daarna uit, wat botst met de beveiligingsregel dat geheugen niet tegelijk beschrijfbaar en uitvoerbaar mag zijn. Runtimes lossen dit op door na het genereren van code de paginapermissies om te schakelen, of door hetzelfde fysieke geheugen twee keer te mappen met verschillende permissies, en sommige dichtgetimmerde platforms verbieden het genereren van code tijdens de uitvoering volledig. Omdat gecompileerde code afhangt van runtimeprofielen, kunnen de prestaties per run verschillen en plotseling dalen bij deoptimalisatie, waardoor benchmarken van systemen met een JIT een goede warm-up vereist.

  2. BTijdens de uitvoering vaak gebruikte delen worden naar machinecode vertaald en ook informatie van tijdens de uitvoering kan worden gebruikt
  3. CEr wordt helemaal geen machinecode gebruikt en bytecode wordt eindeloos instructie voor instructie geïnterpreteerd
Antwoord en toelichting tonen

Antwoord: B. Tijdens de uitvoering vaak gebruikte delen worden naar machinecode vertaald en ook informatie van tijdens de uitvoering kan worden gebruikt

Bij JIT-compilatie wordt eerst bytecode geïnterpreteerd en uitgevoerd, en wanneer delen die vaak worden uitgevoerd (hotspots) worden gevonden, worden deze tijdens de uitvoering naar machinecode gecompileerd. Met informatie van tijdens de uitvoering, zoals welke takken werkelijk worden genomen en welke types worden doorgegeven, zijn gedurfde optimalisaties mogelijk die bij vooraf compileren moeilijk zijn. Er is ook een mechanisme om terug te vallen op interpretatie als de aannames niet blijken te kloppen. Alles vooraf vertalen is AOT-compilatie (ahead-of-time), en uitsluitend interpreteren is een zuivere interpreter.

Veelgestelde vragen

Is JIT-compilatie sneller dan AOT-compilatie?

Dat hangt af van de workload. JIT-code kan bij langlopende programma's AOT-code evenaren of overtreffen omdat ze optimaliseert op basis van echte profielen, maar AOT wint op opstarttijd, geheugengebruik en voorspelbaarheid.

Wat is JIT-warm-up?

De beginperiode waarin code in de interpreter of een baseline-tier draait terwijl de runtime haar profileert en de hot delen compileert. Prestaties die tijdens de warm-up worden gemeten, onderschatten de snelheid in de stabiele toestand.

Wat is deoptimalisatie in een JIT?

Het opgeven van geoptimaliseerde code wanneer een aanname waarop die is gebouwd onjuist blijkt, en het voortzetten van de uitvoering in de interpreter of minder geoptimaliseerde code vanaf het equivalente punt. De runtime kan daarna opnieuw compileren met bijgewerkte profielinformatie.
