什麼是互斥鎖（Mutex）

同一時間只有一個執行緒能持有的鎖。無法取得時讓執行緒休眠並讓出 CPU，鎖被釋放時由作業系統喚醒，是一般常見的實作。

日文名稱: ミューテックス

「互斥鎖（Mutex）」出現在2領域的5道練習題中（嵌入式與韌體, 多核心與同步等）。

這個名詞所屬的領域: 多核心與同步

互斥鎖如何運作

互斥鎖（mutual exclusion lock）通常是一個記憶體字組，記錄鎖是否被持有以及是否有人在等待。在無競爭的情況下，取得鎖只需一個原子指令，例如比較並交換（compare-and-swap），在使用者空間完成，成本約為數十奈秒量級。只有在鎖已被持有時，執行緒才會請求作業系統讓它在等待佇列上休眠；在 Linux 上，這是建構在 futex 系統呼叫之上。解鎖時會檢查是否有等待者，若有，便請求核心喚醒其中一個。互斥鎖有擁有者：只有鎖定它的執行緒才應該解鎖。

互斥鎖與自旋鎖的比較

自旋鎖的等待者會持續執行重試取得鎖的迴圈，因此能在鎖釋放後數奈秒內反應，但整段時間都在消耗其 CPU。互斥鎖的等待者會讓出 CPU，對長時間等待很有效率，但需要一次系統呼叫、一次環境切換以及之後的喚醒，總計通常為數微秒。因此，自旋鎖適合多核心機器上非常短的臨界區段，以及不允許休眠的地方，例如核心的中斷處理常式。在單核心上自旋毫無意義，因為等待者佔用 CPU 時，持有者無法釋放鎖。許多函式庫的互斥鎖是自適應的：先短暫自旋，再進入休眠。

互斥鎖與號誌的比較

計數號誌持有一個整數，最多允許 N 個執行緒通過，因此它是限制資源池存取或在執行緒之間傳送信號的工具。任何執行緒都可以對號誌發出 post，因此號誌沒有擁有者的概念。互斥鎖則限定只有一個持有者，並與鎖定它的執行緒綁定。這種所有權使錯誤檢查成為可能，在即時系統中也使優先權繼承成為可能；單純的號誌無法提供這一點，因為系統無法得知該提升哪個執行緒的優先權。

陷阱：優先權反轉與死結

在即時作業系統（RTOS）中，當高優先權任務等待由低優先權任務持有的互斥鎖，而中優先權任務又搶占了低優先權任務時，就會發生優先權反轉，使高優先權任務無限期延遲。這在 1997 年造成了火星探路者號（Mars Pathfinder）著陸器反覆重置。優先權繼承會暫時將持有者提升到等待者的優先權，藉此解決此問題。另一個典型危險是死結：兩個執行緒各持有一個互斥鎖，並等待對方的鎖。標準的預防方法是以單一、固定的全域順序取得多個互斥鎖。

練習互斥鎖（Mutex）的題目

比較互斥鎖（休眠等待的鎖）與自旋鎖，下列說明何者正確？

  1. A互斥鎖在等待期間會讓出CPU，所以適合長時間等待，但休眠與喚醒需要作業系統的額外負擔
  2. B互斥鎖在等待期間也會持續占用CPU，所以只能用於短時間的等待
  3. C互斥鎖與自旋鎖是相同的東西，只是名稱不同
查看答案與解析

正確答案：A. 互斥鎖在等待期間會讓出CPU，所以適合長時間等待，但休眠與喚醒需要作業系統的額外負擔

互斥鎖在取不到鎖時，會讓執行緒進入等待狀態並把CPU讓給其他執行緒，鎖被釋放時再由作業系統喚醒。由於等待期間不會浪費CPU，適合長時間的等待，但休眠、喚醒的處理與情境切換（context switch）需要數微秒左右。實際的函式庫中的互斥鎖，會先自旋一小段時間再休眠，結合了兩者的優點。

常見問題

互斥鎖和二元號誌有什麼不同？

兩者一次都只允許一個執行緒進入，但互斥鎖有擁有者，必須由擁有者釋放；號誌則任何執行緒都可以發出信號。正是所有權讓互斥鎖能實現優先權繼承與錯誤檢查。

什麼時候應該用自旋鎖而不是互斥鎖？

只有在臨界區段僅有少數幾個指令、持有者正在另一個核心上執行，且休眠不可行或太慢時，才使用自旋鎖。任何可能等待超過數微秒的情況，休眠式互斥鎖都是較好的選擇。

為什麼互斥鎖在競爭激烈時很慢？

每次發生競爭的取得都可能涉及一次系統呼叫、一次環境切換與一次喚醒，而且鎖所在的快取行會在核心之間來回傳遞。縮短臨界區段，或將一個鎖拆分成數個更細粒度的鎖，通常比更換鎖的類型更有幫助。
