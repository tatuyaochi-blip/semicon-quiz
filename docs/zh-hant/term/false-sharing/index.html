什麼是偽共享（False sharing）

不同執行緒各自改寫不同的變數，但因這些變數位於同一條快取行，使得該行在核心之間來回傳遞而變慢的現象。

日文名稱: 偽共有

「偽共享（False sharing）」出現在2領域的4道練習題中（多核心與同步, CPU與架構等）。

這個名詞所屬的領域: 多核心與同步

一致性為何以快取行而非變數為單位

MESI（Modified、Exclusive、Shared、Invalid）等快取一致性協定追蹤的是整條快取行（通常為 64 位元組）的所有權，而非個別變數。核心在寫入之前必須獨占該行，這會使其他所有核心的副本失效。若核心 0 不斷寫入變數 a，核心 1 不斷寫入同一行中的變數 b，每次寫入都會迫使該行在兩個快取之間移動。兩個執行緒都不讀取對方的資料，因此結果仍然正確，但原本只需數個週期的 L1 命中，會變成緩慢的跨核心傳輸。

偽共享與真共享的差異

真共享是指執行緒確實存取同一個變數，例如全域計數器或鎖的字組；這種競爭是本質性的，只能透過改變演算法來消除，例如將計數器拆分。偽共享則是指資料在邏輯上互相獨立，只是剛好在記憶體中相鄰，因此解法是改變資料配置。兩者會產生相同的症狀：少數快取行上出現大量一致性通訊。唯讀共享則不會造成任何問題，因為許多快取可同時以 Shared 狀態持有同一行；只有寫入才會迫使失效。

典型的元凶

典型案例是每個執行緒各一個計數器的陣列：元素為 8 位元組時，一條 64 位元組的快取行可容納 8 個，因此最多會有 8 個執行緒爭奪同一行。其他常見來源包括欄位由不同執行緒更新的結構、與受另一個鎖保護的資料放在同一行的鎖，以及由生產者與消費者分別寫入的頭尾索引相鄰的工作佇列。常見的徵兆是：雖然每個執行緒看似只存取自己的資料，但隨著執行緒增加，程式的加速比卻趨於平緩甚至下降。

如何修正與找出偽共享

將每個獨立寫入的項目填充或對齊到快取行大小，例如在 C 或 C++ 中使用 alignas(64)，讓每個執行緒擁有自己的快取行。有些處理器會成對擷取相鄰的快取行，這就是有時會使用 128 位元組間隔的原因。更好的做法是讓每個執行緒在區域變數或暫存器中累加，最後只寫入共享位置一次。硬體效能計數器可以揭露此問題；在 Linux 上，perf c2c 工具會回報經常被某個核心修改、隨後又被另一個核心存取的快取行。

練習偽共享（False sharing）的題目

關於多執行緒程式中發生的偽共享（false sharing），下列說明何者正確？

  1. A不同的執行緒雖然改寫不同的變數，但因為這些變數位於同一條快取列，使快取列在核心之間來回移動而變慢
  2. B兩個執行緒未經同步就改寫同一個變數，導致值被破壞
  3. C執行緒彼此等待對方的鎖而停住
查看答案與解析

正確答案：A. 不同的執行緒雖然改寫不同的變數，但因為這些變數位於同一條快取列，使快取列在核心之間來回移動而變慢

一致性是以快取列（一般為64位元組）為單位管理的。即使核心0只是改寫變數a、核心1只是改寫變數b，若a與b位於同一條快取列，每次寫入都會使對方的副本失效，快取列就會在兩個核心之間來回移動。明明結果正確，效能卻大幅下降，這就是偽共享。這是在每個執行緒各自的彙總用陣列等情況中容易發生的問題。

像「long cnt[8];」這樣排列每個執行緒的計數器陣列，發生了偽共享。下列何者是最適當的對策？

  1. A把計數器的型別從long改為int，縮小陣列
  2. B在各計數器之間加入填充或進行對齊，使它們放在不同的快取列
  3. C增加執行緒的數量，分散等待時間
查看答案與解析

正確答案：B. 在各計數器之間加入填充或進行對齊，使它們放在不同的快取列

若long為8位元組，8個計數器就會收進64位元組的一條快取列，所有執行緒都會爭奪同一條快取列。只要加入填充使各計數器每隔64位元組放置，或將結構對齊到快取列的大小，每個執行緒就能使用各自不同的快取列。此外，讓各執行緒以區域變數計數，最後只加總到共用位置一次，也是有效的方法。

常見問題

偽共享會導致錯誤的結果嗎？

不會。一致性協定會讓每個變數保持正確；偽共享只會耗費時間，因為存放這些變數的快取行會不斷在核心之間移動。

要避免偽共享需要多少填充？

填充到讓每個獨立寫入的變數各佔一條快取行即可，通常為 64 位元組。有些程式使用 128 位元組，因為某些 CPU 會成對預取相鄰的快取行。

唯讀的共享資料會造成偽共享嗎？

不會。多個核心可以同時以共享狀態保有同一條快取行；只有在至少一個執行緒寫入該行時才會出現問題。
