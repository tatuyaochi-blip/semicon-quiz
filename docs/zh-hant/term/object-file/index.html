什麼是目的檔（Object file）

編譯器從單一原始碼檔案輸出的檔案。包含機器碼、資料的初始值、符號表與重定位資訊，但其他檔案的位址尚未確定，不經連結就無法執行。

日文名稱: オブジェクトファイル

「目的檔（Object file）」出現在2領域的9道練習題中（連結器與載入器與執行檔格式, 編譯器等）。

這個名詞所屬的領域: 連結器與載入器與執行檔格式

目的檔裡有什麼

目的檔由多個區段組成。text 區段存放機器碼；data 區段存放已初始化的可寫入變數；唯讀資料區段存放常數與字串字面值；bss 區段則只記錄初始值為零之變數的大小，因此在檔案中不佔空間。除此之外，符號表列出檔案定義的每個名稱，以及檔案使用但未定義的每個名稱；重定位項目則列出之後必須填入位址的每個位置。除錯資訊是選用的。常見格式有 Linux 的 ELF、macOS 的 Mach-O，以及 Windows 的 COFF/PE。

為什麼它無法單獨執行

編譯器或組譯器會各自獨立地建立每個目的檔，並將其區段配置成彷彿從位址 0 開始。當程式碼呼叫其他檔案中的函式（例如 printf）時，其位址是未知的，因此指令中會放入預留值（通常為 0），再加上一筆描述該處應填入什麼的重定位項目。只有連結器能同時看到所有目的檔與函式庫。它會將每個未定義符號與其定義配對、決定每個區段在記憶體中的位置、修補預留值，並加入作業系統載入程式所需的啟動程式碼與標頭。

典型的連結錯誤及其意義

undefined reference to foo 這類錯誤，表示某個目的檔使用了 foo，但連結對象中沒有任何地方定義它。常見原因包括忘了連結定義它的檔案、漏掉 -lm 等函式庫選項、名稱拼錯，或從 C++ 呼叫 C 程式碼時沒有使用 extern "C"，導致名稱在 C++ 的名稱修飾後不一致。反過來的 multiple definition 錯誤，通常是因為在被多個原始碼檔案引入的標頭檔中定義了變數。使用 GNU 連結器時，命令列上的靜態函式庫應放在使用它們的目的檔之後。

目的檔、靜態函式庫與共享函式庫

靜態函式庫只是目的檔的封存檔。連結器只會取出能解析目前未定義符號的成員，這就是命令列順序很重要的原因。共享函式庫則不同：它本身已是連結的產物，由位置無關程式碼建構而成，在執行時被映射到記憶體中，其餘的位址由動態連結器填入。nm、objdump 與 readelf 等工具可顯示目的檔的區段、符號與重定位項目，是找出連結失敗原因最快的方法。

練習目的檔（Object file）的題目

關於編譯器從單一原始檔輸出的目的檔（.o），下列何者正確？

  1. A是可直接在作業系統上執行的完整程式
  2. B只是將原始碼壓縮而成，不含機器碼
  3. C含有機器碼，但其他檔案中的函式與變數的位址尚未決定
查看答案與解析

正確答案：C. 含有機器碼，但其他檔案中的函式與變數的位址尚未決定

目的檔中包含該檔案內函式經翻譯後的機器碼、變數的初始值、所定義與所參照的名稱清單（符號表），以及事後要填入位址的位置清單（重定位資訊）。像printf這樣呼叫其他檔案中函式的指令，由於不知道位址，仍保留暫時的值。連結器會將多個目的檔整合起來決定位址，進而產生執行檔。

使用GNU連結器時，若像「gcc -lmylib main.o」這樣，將靜態函式庫寫在使用它的目的檔之前，有時會出現未定義參照的錯誤。下列關於其原因的敘述何者正確？

  1. A因為連結器從左到右依序處理，讀取函式庫的時點上尚未被參照的函式不會被取出
  2. B因為規定函式庫必須且只能寫在指令的最後一個
  3. C因為將函式庫寫在前面，函式庫的內容會被清除
查看答案與解析

正確答案：A. 因為連結器從左到右依序處理，讀取函式庫的時點上尚未被參照的函式不會被取出

GNU連結器依命令列上所寫的順序處理檔案，遇到靜態函式庫時，只會取出能解決「尚未找到定義的參照」的目的檔。若先寫函式庫，在那個時點main.o的參照還不存在，所以什麼都不會取出，之後再讀取main.o也不會回頭尋找。因此原則上函式庫要寫在使用它的一方之後。

常見問題

目的檔和可執行檔有什麼差別？

目的檔包含單一原始碼檔案的機器碼，但對其他檔案的參考尚未解析，也沒有最終位址。可執行檔是連結器的輸出，所有符號都已解析、位址已確定，並帶有告訴作業系統如何載入它的標頭。

怎麼列出目的檔中的符號？

使用 nm、objdump -t 或 readelf -s。在 nm 的輸出中，標示為 U 的符號是未定義的，表示該檔案參考了它們，並預期由其他目的檔或函式庫來定義。

bss 區段是什麼？

它存放初始值為零的全域變數與靜態變數。目的檔只記錄其大小，程式啟動時再由載入器配置記憶體並填入零。
